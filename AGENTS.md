# Правила проекта

Перед изменениями читайте README.md, docs/mvp.md, docs/requirements.md и связанные вопросы в docs/open-questions.md. Сохраняйте полезную реализацию. Не придумывайте правила очереди, бронирования и заселения. Не считайте заглушки, ручные операции и локальный вход выполнением интеграций.

## Архитектура

- Проект — модульный монолит на Go, SQLite, серверных HTML-шаблонах и CSS.
- `cmd/server` отвечает за запуск, сигналы и корректное завершение процесса.
- `internal/app` собирает зависимости через конструкторы и регистрирует маршруты. Здесь нет SQL или бизнес-правил.
- `internal/platform` содержит конфигурацию, БД, применение миграций, HTTP middleware, рендеринг и техническую работу с файлами. Платформа не импортирует бизнес-модули или `internal/app`.
- `internal/modules/<module>` содержит HTTP-обработчики, сервисы с бизнес-логикой и репозитории для БД в отдельных файлах. Обработчик разбирает запрос, вызывает сервис и формирует ответ. SQL запрещён в обработчиках, маршрутах и сервисах.
- Сервис принимает предметные типы и контекст, не импортирует `net/http`, обработчики, маршруты или HTML-шаблоны. Репозиторий реализует SQL через параметризованные запросы. Значимые изменения состояния выполняются транзакционно.
- Зависимости передаются явно через конструкторы. Не используйте изменяемые глобальные зависимости или service locator. Конкретные реализации связываются в `internal/app`. Узкие интерфейсы объявляются у потребителя там, где требуется замена реализации; не создавайте интерфейс для каждого типа.
- Не создавайте пустые модули для будущих функций. Межмодульные обращения проходят через явный контракт, без чтения чужих таблиц в HTTP-слое.
- `web/templates` содержит HTML с общим шаблоном; используйте `html/template` и обычное экранирование. Пользовательский ввод не становится доверенным HTML. `web/static` содержит только публичные файлы; рабочее хранилище не публикуется статическим маршрутом.
- `migrations` содержит последовательные SQL-файлы `000001_name.sql`, `000002_name.sql` и далее без пропусков. Применённые файлы неизменяемы; исправления добавляются следующей миграцией. Первая миграция создаёт журнал и должна оставаться идемпотентной. Применение миграций находится в платформе.
- Права проверяются сервером. Технический HTTP-журнал не заменяет бизнес-аудит.
- Деловое изменение и обязательное событие аудита выполняются через `audit.Recorder.RecordChange` в одной транзакции. Репозитории внутри callback используют переданный `*sql.Tx`, не исходную БД; callback не фиксирует транзакцию самостоятельно. Передавайте контекст во все операции БД. Не отключайте внешние ключи на соединениях.
- Не журналируйте пароли, токены, тела документов, анкеты, заголовки, тела запросов и произвольные значения паник или ошибок с данными пользователя. Для корреляции используйте серверный `request_id`, для маршрута — его шаблон. Событие аудита содержит идентификаторы и коды, не чувствительный payload. Транзакционный контракт описан в `docs/sqlite.md`.

## Проверка и документация

Используйте подходящие существующие зависимости и стандартную библиотеку. Обновляйте `.env.example` и README при изменениях настроек или команд. Секреты, `.env`, БД, рабочие файлы и бинарники не коммитятся.

Перед завершением выполните `gofmt -w cmd internal migrations web`, `go test ./...`, `go vet ./...` и `go build -o bin/server ./cmd/server`. Для изменений транзакций, прав, ошибок и завершения проверяйте соответствующее поведение. Требования отмечайте реализованными только с подтверждением; у составного пункта сохраняйте остаток.

Для auth используйте постоянный локальный ID и отдельные внешние идентичности. Не принимайте роль или user_id из формы. Все изменяющие маршруты подключайте через общую CSRF-защиту; для деловых операций проверяйте разрешение и назначенное общежитие также в сервисе. Системный администратор не имеет обхода прав на деловые данные. Тестовые пользователи создаются cmd/dev-users или автоматически после миграций при включённом development-входе; существующие пользователи и данные входа не перезаписываются. Тестовый вход и автозаполнение запрещены вне development. Production-cookie всегда Secure; настройки не выводятся из недоверенных proxy-заголовков. SSO остаётся отложенным.

В inventory постоянные ID и родители не меняются при редактировании. Корневое общежитие создаётся только для предварительно назначенного ID. Проверяйте всю фактическую цепочку родителей и разрешения внутри транзакции, используя AuthorizeTx, а не соединение исходной БД. Деньги — int64 минимальных единиц с явными валютой и периодом, без float. Номер комнаты уникален на этаже, в том числе в архиве. Не добавляйте каскадное удаление или скрытое архивирование детей; сохраняйте версии и снимки полей в аудите. Фотографии и койко-места на этом шаге не реализованы.
