# Пользователи и доступ

Модуль `internal/modules/auth` разделён на HTTP-обработчики, сервис, SQL-репозиторий, проверку development-пароля и создание тестовых пользователей. Новых зависимостей нет. Миграция `000003_auth.sql` добавляет пользователей, внешние идентичности, роли, разрешения, назначения общежитий и серверные сессии. При включённом development-входе сервер после миграций автоматически заполняет пять тестовых ролей; production не заполняется.

## Постоянная идентичность

`auth_users.id` — случайный постоянный локальный ID. Пара `(provider, subject)` хранится отдельно в `auth_external_identities` и может принадлежать только одному пользователю. Несколько идентичностей могут ссылаться на один локальный ID. Права и аудит опираются на локальный ID, а не на логин или будущий SSO subject. Неизвестная идентичность development/будущего SSO не создаёт пользователя автоматически и не связывается по совпадению имени. Исключение по запросу от 16.11.2026 — проверенный ИИН НУЦ РК: неизвестный ИИН создаёт студента через отдельный ЭЦП-сценарий ([eds-login.md](eds-login.md)).

Сервис входа принимает `IdentityVerifier`, проверяющий доказательство одной попытки и возвращающий идентичность. Для тестовых паролей используется development-адаптер; вход с ЭЦП имеет отдельный challenge-сценарий и серверный адаптер NCANode. Будущий SSO-адаптер должен проверять свой протокол и передавать доверенную идентичность; HTTP-форма не задаёт provider, subject, локальный ID или роль. Тест замены адаптера проверяет модель связи, не готовность SSO. SSO по 2.5 остаётся **отложенным**: OIDC/SAML, проверка внешних подписей и интерфейс связывания не реализованы.

## Тестовые пользователи

Из корня, на development-БД:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true go run ./cmd/server
```

После миграций создаются пять пользователей с аудитом одной транзакцией. Откройте `/auth/login`, возьмите данные из `var/dev-users.txt`. По умолчанию TXT находится рядом с `DATABASE_PATH`; `DEV_USERS_FILE` задаёт другой путь. Он содержит роль, логин, индивидуальный пароль и постоянный локальный ID. Сотрудникам назначается `dev-dorm-1`, без создания фиктивного общежития. Полный существующий набор сохраняется без изменения паролей, ролей, назначений и состояния enabled; повторного события создания нет. Удалённый файл не восстанавливается из хешей. Частичный набор автоматически не дополняется, запуск завершается ошибкой без изменений.

Для первоначального заполнения с собственными назначениями сохранена отдельная команда; выполните её до первого запуска сервера с включённым входом:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true go run ./cmd/dev-users -out var/dev-users.json -dormitories dev-dorm-1,dev-dorm-2
```

У набора, созданного командой, данные остаются в её JSON-файле: сервер не перезаписывает пользователей и не создаёт TXT с новыми паролями.

Файлы содержат секреты: используйте исключённый из Git каталог `var` или `secrets`. Маска `dev-users*.txt` явно добавлена в `.gitignore`. Права нового файла — `0600`, каталога — `0700`. Пароли не выводятся в терминал или технические логи. Существующие файл и логины не перезаписываются. Для отдельного набора используйте новую development-БД и новый файл.

Создаются `dev_student`, `dev_registry_staff`, `dev_commandant`, `dev_administration`, `dev_system_admin`. Для каждого генерируются отдельный пароль из 32 случайных байтов и отдельная соль. В БД хранится производный ключ PBKDF2-HMAC-SHA256, 600000 итераций; сравнение выполняется за постоянное время. Коэффициент указан в [рекомендациях OWASP для PBKDF2](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2). Общих и fallback-паролей нет.

Пользователи, идентичности, хеши, назначения и аудит создания сохраняются одной транзакцией. При обработанной ошибке записи файла или аудита БД откатывается, созданный файл удаляется. Файл и SQLite не образуют общей транзакции файловой системы: при аварии между записью файла и фиксацией БД файл может остаться; запуск не объявляется успешным. После такой аварии сохраните файл для диагностики и используйте согласованный набор БД и файла; автоматического сброса паролей нет. Заполнение выполняется после миграций отдельной транзакцией: ошибки заполнения не откатывают уже применённую схему. SQL-миграции общие для окружений и не содержат тестовых паролей или пользователей.

## Тестовая матрица

Это матрица проверки инфраструктуры, а не утверждённый регламент production по Q-07.

| Роль | Глобальные права | Права в назначенных общежитиях |
| --- | --- | --- |
| Студент | `account.read` — свой кабинет | Нет |
| Сотрудник реестра | `account.read` | `registry.read`, `registry.write`, `registry.export` |
| Комендант | `account.read` | `registry.read`, `places.status.write` |
| Администрация | `account.read` | `registry.read`, `registry.export`, `statistics.read`, `audit.read` |
| Системный администратор | `account.read`, `auth.users.read`, `auth.users.roles.write` — просмотр учётных записей и смена ролей | Нет |

У системного администратора нет обхода проверок. Даже назначение общежития не даёт ему права на фонд, аудит или статистику. Для scoped-разрешения нужны и право, и назначение целевого общежития. Неизвестные разрешения запрещены. Роли и назначения читаются из БД при каждом запросе; отзыв действует без повторного входа.

Назначения находятся в `auth_user_dormitories`. ID может быть назначен до внесения общежития в inventory; это резервирование области доступа, а не фиктивная запись фонда. После создания inventory использует этот постоянный ID и проверяет фактическую цепочку родителей в БД. Операции общежитий, корпусов, этажей и комнат реализованы в [inventory](inventory.md) с проверками прав в сервисе и внутри транзакции. Койко-места и административные статусы реализованы: создание и характеристики требуют `registry.write`, смена статуса — `places.status.write`, совместно с `registry.read` и назначением общежития. В тестовой матрице статусы меняет комендант, сотрудник реестра только ведёт структуру. История места доступна с `registry.read`; общий просмотр аудита и статистика ещё не реализованы. Смена ролей через сайт описана ниже; редактора назначений общежитий пока нет.

## Сессии и CSRF

Токен сессии содержит 32 случайных байта. В SQLite хранятся его SHA-256, отдельный ID записи, пользователь, источник идентичности, CSRF-токен, время создания и абсолютное время окончания. В cookie нет ролей, прав или анкеты. `SESSION_TTL` по умолчанию `8h`, допустимо от `1s` до `24h`; срок проверяется сервером, продления при активности нет. Истёкшие записи не авторизуют запросы; периодическая очистка таблицы пока не добавлена.

Форма входа получает анонимную серверную сессию на 10 минут и synchronizer CSRF token. Успешный вход удаляет прежнюю сессию, создаёт новые токен и CSRF. Вход и выход сохраняются с аудитом в общей транзакции. Пароли, cookie и CSRF не попадают в аудит или технические логи.

Все зарегистрированные изменяющие формы защищаются при сборке маршрутов: Origin/Sec-Fetch-Site проверяются через `http.CrossOriginProtection`, а скрытое POST-поле `csrf_token` сравнивается с токеном сессии. Значение из query string не принимается. Размер тела ограничен 64 KiB; отдельные поля дополнительно проверяются сервисами. Защищены и вход, и выход. Выход доступен только через POST и удаляет серверную сессию; очистка cookie не заменяет отзыв.

В development cookie `dorm_session` имеет `HttpOnly`, `SameSite=Lax`, `Path=/`, `Expires` и `Max-Age`, без `Secure` для локального HTTP. В production используется `__Host-dorm_session` с обязательным `Secure` и без `Domain`. Значение Secure определяется конфигурацией, не заголовком `X-Forwarded-Proto`. Production обслуживается через HTTPS на доверенном обратном прокси, сохраняющем Host; TLS-терминации в Go-сервере пока нет.

`DEV_LOGIN_ENABLED=false` по умолчанию. При выключении development-сессии не принимаются; `/auth/login` остаётся доступным только при настроенном NCANode. Production с включённым тестовым входом отклоняется и при загрузке окружения, и при сборке приложения, до открытия БД. Команда dev-users также запрещена в production. В production доступен вход с ЭЦП при настроенном NCANode; без него способ входа отсутствует. Это не реализация вузовского SSO.

## Защищённые маршруты

| Маршрут | Проверка |
| --- | --- |
| `GET /auth/login`, `POST /auth/login` | GET при настроенном NCANode или development-входе; POST пароля только в development, с сессией и CSRF. |
| `GET /account` | Действующая сессия и `account.read`, свой профиль. |
| `POST /auth/logout` | Действующая пользовательская сессия, CSRF и аудит удаления. |
| `GET /admin/users` | `auth.users.read`; имена, ID и текущие роли, без паролей, хешей и токенов. |
| `POST /admin/users/{userID}/role` | `auth.users.roles.write`, CSRF и повторная проверка в транзакции. |
| `GET /account/notifications` | `account.read`; только собственные уведомления, для всех ролей. |
| `POST /account/role-notifications/{notificationID}/read` | `account.read`, CSRF, владелец и аудит. Чужой ID — 404. |
| `GET /staff/dormitories/{dormitoryID}` | `registry.read` и назначение ID; карточка общежития и список корпусов. |

Чтение поддерживает HEAD. Прямой запрос без входа возвращает 401, отсутствие полномочий или неверный CSRF — 403, неизвестный путь — 404, неверный метод — 405. Будущие бизнес-сервисы также должны вызывать `Authorize` и проверять принадлежность комнаты или места целевому общежитию. Переданный клиентом ID не доказывает принадлежность.

`go test ./...` проверяет пять ролей, прямые URL, подмену ID и SQL-подобные значения, отзыв назначения, отключение пользователя, истечение сессии, ротацию, выход и replay cookie, отсутствующий/старый/чужой CSRF, чужой Origin, production-флаги, cookie, отсутствие секретов в логах, откат входа и выхода при ошибке аудита, сохранение ID при замене адаптера, закрытый файл и отказ перезаписи. `internal/app/development_test.go` проверяет автозаполнение после миграций, работоспособность пяти паролей, повторный запуск без сброса доступа, откат при ошибках файла/аудита, отказ для частичного набора и отсутствие заполнения вне включённого development-входа.

## Навигация интерфейса

Общее меню и быстрые переходы в кабинете строятся из текущих разрешений и назначенных общежитий. Скрытие ссылок дополняет серверные проверки. Выход с CSRF доступен из шапки всех HTML-страниц после входа. Список учётных записей содержит поиск по имени или ID и сброс; в карточке кабинета показаны роли и срок сеанса. Ошибка входа возвращает ту же форму с сохранённым логином, пустым паролем и действующим CSRF. Страницы 401/403/404 предлагают вход или переход в кабинет и на главную. Отсутствующие функции фонда помечены как разрабатываемые, без фиктивных действий.

Навигация пяти ролей на главной, в кабинете и на странице ошибки, фильтрация списка, пустое состояние и повтор входа проверяются в `internal/app/navigation_test.go`. Также проведена визуальная проверка узкой и широкой версии на отдельной development-БД.

Миграция `000007_registry_export.sql` добавляет отдельное scoped-разрешение `registry.export` сотруднику реестра и администрации. Статистика и история используют существующие `statistics.read`/`audit.read`; все три требуют также `registry.read` и актуального назначения, проверяемых в одном срезе через `AssignedDormitoriesTx`/`AuthorizeTx`. Системный администратор не получает доступ к деловым данным. Контракт и проверки — [reports.md](reports.md).


Расширение applications: миграция 000008 добавляет нескоупированное разрешение `applications.own` только роли student в текущей тестовой матрице. Оно позволяет работать только с собственным профилем и заявлениями; объектная проверка владельца обязательна и выполняется сервисом/репозиторием, при изменениях разрешение повторно проверяется через AuthorizeTx. По applications.own сотрудники и системный администратор не получают доступа к заявлениям; отдельные назначенные маршруты проверки описаны ниже. Назначение общежития не требуется: заявления не выбирают фонд. [Контракт и проверки](applications.md).

Расширение 000009: applications.review у registry_staff позволяет читать/проверять только фактически назначенные заявления и их версии файлов; applications.assign у administration позволяет работать только с метаданными назначения. Все изменения повторно проверяют разрешение и владельца/назначение внутри транзакции; GET/HEAD файлов также проверяются в транзакции. Переназначение немедленно закрывает новые запросы прежнего проверяющего. Системный администратор не имеет обхода. Это development-матрица, а не утверждённая производственная политика; [контракт](application-review.md).


## Управление ролями

По запросу пользователя от 16.11.2026 миграция `000010_user_roles.sql` добавляет `auth.users.roles.write` только роли `system_admin`, версию ролей пользователя и внутренние уведомления. На `/admin/users` в столбце «Роли» показаны текущие роли и выпадающий список всех ролей справочника. Выберите роль и нажмите «Сохранить роль». Поиск и язык сохраняются после отправки.

Выбранная роль заменяет весь текущий набор ролей одного пользователя. Существующие множественные роли показаны полностью; для их замены требуется явный выбор. Сохранение единственной текущей роли не создаёт уведомление, аудит или новую версию. Устаревшая версия формы отклоняется с 409 и обновлённым списком; неизвестная роль — 422, неизвестный пользователь — 404. Последнему активному `system_admin` нельзя снять эту роль, в том числе самому себе: сначала нужно назначить другого активного администратора. Отключённый администратор не считается заменой.

Автор берётся только из серверной сессии, получатель — из пути. `role_id` здесь является командой авторизованного администратора; это исключение для редактора ролей по прямому запросу пользователя, а не способ задать собственную роль при входе или в других формах. Сервис повторно проверяет `auth.users.roles.write` через `AuthorizeTx`. Роль, версия, уведомление и событие `auth.user_role_changed` сохраняются одной транзакцией `audit.Recorder.RecordChange`. Аудит содержит ID автора/получателя и коды ролей до/после; имена, анкеты и секреты в него не копируются. Сбой уведомления или аудита откатывает всё изменение.

Постоянный ID, внешние идентичности, пароли, сессии и назначения общежитий сохраняются. Новые права действуют при следующем запросе существующей сессии. Назначение роли само по себе не назначает общежитие и не даёт `system_admin` обхода деловых разрешений.

Получатель видит «Ваша роль изменена», новую роль и время на `/account/notifications`, доступном всем ролям. В меню и кабинете отображается число непрочитанных уведомлений о роли. Прочтение — явный POST с CSRF; чужое уведомление возвращает 404, повтор сохраняет исходную дату без повторного аудита. Ранее полученные уведомления заявлений остаются собственностью пользователя и доступны после смены роли, но переход к заявлению по-прежнему требует его текущих деловых прав. Внешние email/SMS/push-каналы не подключены.

Проверки: `internal/modules/auth/roles_migration_test.go` — обновление существующей БД без сброса ID, ролей, состояния enabled, назначений, идентичностей, паролей и сессий; `internal/modules/auth/roles_test.go` — разрешения и отзыв, несколько ролей, последний администратор, версия/конкуренция, отсутствие дублей, собственность/прочтение и откаты; `internal/app/roles_test.go` — POST/CSRF/Origin, подмена автора/получателя, RU/KK, текущая сессия, уведомление, прочтение и сохранность после restart с development-автозаполнением. Это ограниченное дополнение к Q-07/Q-08/Q-22; создание/отключение пользователей через сайт, редактор назначений, производственная матрица и SSO остаются отдельным объёмом.

Итоговая проверка расширения: `gofmt -w cmd internal migrations web`, `go test ./...`, `go vet ./...` и `go build -o bin/server ./cmd/server` выполнены успешно, включая существующий процессный тест restart/SIGTERM. Тесты используют временные БД; рабочие данные не изменялись.


## Вход по сертификату НУЦ РК

По запросу от 16.11.2026 добавлены проверка NCALayer, одноразовая подпись запроса входа, серверный адаптер NCANode/OCSP, автоматический студент по новому ИИН и данные кабинета из сертификата. Для известных NCA-идентичностей все роли используют тот же вход; отключённые аккаунты не пересоздаются. Связь существующих ID и первое назначение администратора выполняются офлайн через `cmd/eds-account`, с аудитом. Транзакции, команды и ограничения доказательств описаны в [eds-login.md](eds-login.md). Настоящий NCANode и пользовательский ключ ещё требуют сквозной проверки; SSO и прочие интеграции не объявлены завершёнными.
