# Согласованная копия SQLite и закрытых файлов

Реализована явная CLI-команда `cmd/backup` с действиями `create`, `verify`, `restore`. Резервирование и восстановление проверены на отдельном наборе данных, включая неподтверждённые checkpoint-ом, но зафиксированные в WAL записи. Это ручной офлайн-способ для одного экземпляра приложения на macOS/Linux и локальном постоянном диске.

## Порядок работы

1. Остановите сервер через Ctrl+C или SIGTERM и дождитесь `server stopped gracefully`. Остановите также `dev-users`, `demo-data`, внешние SQLite-клиенты и ручные операции с фотографиями и документами. Для старого бинарника без новых блокировок остановка также обязательна.
2. Создайте копию в **новой** папке вне `FILES_DIR`. Исходные `DATABASE_PATH` и `FILES_DIR` должны соответствовать одной рабочей паре.
3. Выполните `verify` и сохраните всю папку копии. Проверяйте копии после переноса и периодически выполняйте пробное восстановление.
4. Восстанавливайте только в **новую** папку, затем запускайте сервер с обоими новыми путями. Прежняя рабочая папка и папка копии не заменяются.

Пример из корня проекта после остановки сервера:

```sh
DATABASE_PATH="$PWD/var/demo/dormitory.db" \
FILES_DIR="$PWD/var/demo/files" \
go run ./cmd/backup create -out var/backups/mvp-001

go run ./cmd/backup verify -from var/backups/mvp-001

go run ./cmd/backup restore \
  -from var/backups/mvp-001 -out var/restored-mvp-001

APP_ENV=development DEV_LOGIN_ENABLED=true HTTP_ADDR=127.0.0.1:8090 \
DATABASE_PATH="$PWD/var/restored-mvp-001/dormitory.db" \
FILES_DIR="$PWD/var/restored-mvp-001/files" \
DEV_USERS_FILE="$PWD/var/demo/dev-users.txt" \
go run ./cmd/server
```

`verify` и `restore` используют явно переданную папку и не читают настройки рабочей БД из окружения. `create` использует `DATABASE_PATH`/`FILES_DIR`. Для production-копии не включайте development-вход; само резервирование не создаёт пользователей или фонд. Папки `mvp-001` и `restored-mvp-001` должны отсутствовать до команды, даже пустые существующие папки не перезаписываются.

## Почему это учитывает WAL и фотографии

Сервер, команда пользователей, демо и создание/восстановление копий используют advisory-lock-файлы для пары БД и хранилища. Блокировки удерживаются до закрытия БД/окончания команды; второй процесс с той же БД **или** хранилищем получает отказ. Папки с незавершённой операцией имеют `.maintenance-incomplete`; сервер отказывается запускаться с ними. Lock-файлы сохраняются после нормального выхода, но ОС снимает блокировку при закрытии процесса или аварии. Удалять lock-файл для обхода занятого набора нельзя.

Дополнительно `create` удерживает SQLite `BEGIN IMMEDIATE` на отдельном соединении без изменений строк. Это блокирует SQLite-писателей на время чтения снимка и копирования файлов. Загрузка/удаление/очистка фото в приложении выполняются под той же транзакционной блокировкой, поэтому файл не может исчезнуть между снимком метаданных и копированием. Прямые изменения файлов внешними инструментами не входят в этот контракт.

Сама копия SQLite создаётся **другим read-only-соединением** через параметризованный `VACUUM INTO ?`, а не `cp` главного `.db`. Получается самостоятельный снимок подтверждённого содержимого, включая WAL. Операция не выполняется внутри удерживающей блокировку транзакции. Свойства `VACUUM INTO` описаны в [официальной документации SQLite](https://www.sqlite.org/lang_vacuum.html). Исходный WAL вручную не удаляется; предположение об обязательном checkpoint перед копированием не используется.

Перед копированием проверяются текущий журнал миграций с SHA-256 встроенных файлов, `PRAGMA integrity_check` и `PRAGMA foreign_key_check`. Рабочая БД не мигрируется командой резервирования. Из снимка составной контракт app.BackupReferences получает перечень фотографий inventory (включая архивные и неопубликованные) и всех версий документов applications (включая отозванные заявления). Копируются только эти файлы, без бесхозных файлов, plaintext-паролей, `.env` и посторонних рабочих файлов. Для каждого файла сверяется размер из БД и считается SHA-256; симлинки, неверные ключи и выход за пределы папки не принимаются.

## Формат и восстановление

```text
mvp-001/
  manifest.json        версия формата 1, время UTC, размеры и SHA-256
  dormitory.db         самостоятельная SQLite, без необходимых sidecar-файлов
  files/photos/...     все фотографии, на которые ссылается снимок БД
  files/documents/...  все версии электронных документов из снимка БД
```

Новые папки — 0700, БД, изображения и manifest — 0600. Файлы и каталоги синхронизируются с диском; маркер незавершённой операции снимается только после записи всего набора. При ошибке, отмене или аварии неполная папка может остаться; её нельзя использовать как успешную копию. Повторите операцию в новую папку, не удаляя маркер для обхода проверки.

`verify` отказывается от незавершённой папки, неизвестного формата, неверных путей, JSON с дополнительным payload, несовпадения checksum/размеров, неожиданного `-wal`/`-shm`/`-journal`, ошибок БД/миграций/внешних ключей и несовпадения manifest с перечнем фотографий и документов в БД. `restore` сначала выполняет эту проверку, создаёт новую папку с маркером и удерживает блокировки, повторно сверяет хеши при копировании, проверяет БД и только затем разрешает запуск. Пути копии и восстановления не должны пересекаться. Никакие существующие рабочие файлы не заменяются.

SQLite содержит существующие локальные ID, внешние идентичности, хеши паролей, назначения, сессии, фонд, историю и аудит. Текстовый development-файл паролей, `.env`, сертификаты и другие секреты не включаются. В примере восстановленный development-набор использует сохранённый **исходный** `dev-users.txt`; существующие пользователи и пароли при запуске не переписываются. Эксплуатационное хранение конфигурации и секретов организуется отдельно.

## Проверки и ограничения

- `internal/platform/backup/backup_test.go`: отдельный непустой WAL при устаревшем основном файле; сохранение подтверждённых строк; блокировка параллельного писателя; точные байты фотографий; исключение бесхозных файлов; восстановление, права файлов, отказ перезаписи и пересечения путей; повреждение/удаление фото, БД и manifest; симлинки, traversal, sidecar, отмена и маркер незавершённости.
- `internal/platform/maintenance/lock_test.go`: исключение второго процесса по БД и по общему хранилищу, освобождение блокировок, запрет запуска неполного набора.
- `internal/app/acceptance_test.go`: сравнение всех ID, полей, версий, метаданных фото, полной истории мест и событий аудита до/после рестарта и восстановления; затем реальный вход прежними паролями, права, CSRF, фото и обновление каталога.
- `cmd/backup/main_test.go`: воспроизводимые CLI create/verify/restore и отказы на ошибочных аргументах/существующей папке.

Формат пока требует точного совпадения истории миграций с используемым бинарником. Архивы прежних версий сначала проверяются/восстанавливаются соответствующей версией приложения, затем отдельно обновляются обычными миграциями. Схема миграций командой backup не исправляется.

SHA-256 обнаруживает случайное повреждение и подмену отдельных файлов, но не удостоверяет происхождение набора от злоумышленника, способного переписать весь manifest и БД. Копии содержат закрытые данные; автоматическое шифрование, расписание, удалённое хранение, ротация, RPO/RTO и испытание восстановления на эксплуатационном объёме не реализованы/не согласованы. Файловые advisory-блокировки не защищают от администратора ОС и внешних инструментов, игнорирующих протокол; сетевые ФС и Windows не проверены и этим способом не поддерживаются.

С 16.11.2026 команда backup включает отдельный `files/documents/` для PDF/JPEG/PNG и всех сохранённых версий. Схема копии должна совпадать с бинарником backup. Для старой копии используется соответствующий прежний бинарник; затем новый сервер мигрирует восстановленную рабочую БД. `internal/app/application_review_test.go` проверяет backup/restore двух версий и защищённую выдачу прежней версии после восстановления. Персональные поля, комментарии, назначения, результаты и уведомления находятся в SQLite; документные байты — в закрытом хранилище, всё входит в согласованный набор.
