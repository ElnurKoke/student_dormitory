# Профиль студента и локальные заявления

Добавлено по запросу от 15.11.2026 как отдельное расширение после первого этапа; 16.11.2026 дополнено [документами и ручной проверкой](application-review.md). Рабочий сценарий использует существующий development-вход `dev_student`, постоянный локальный ID, серверную сессию и общую CSRF-защиту. Миграция `000008_applications.sql` добавляет разрешение `applications.own` только роли student; существующие пользователи, пароли и назначения не перезаписываются. Это тестовая матрица, не утверждённая production-политика и не SSO.

## Профиль и данные

`/student/profile`: ФИО (до 200 символов), email (до 254, проверяется синтаксис без подтверждения адреса), учебная группа (до 100). Дата рождения, социальные основания и медицинские данные здесь не собираются. По расширению ЭЦП ИИН отдельно хранится в закрытой идентичности auth и показывается владельцу в кабинете; в `fields_json` профиля и снимки заявлений ИИН не копируется; на `/student/profile` он показывается отдельным полем из проверенной идентичности auth ([eds-login.md](eds-login.md)). Это минимальный рабочий состав, предложенный реализацией; окончательный состав требует согласования Q-12/Q-22.

Введённые вручную поля имеют источник **«введено студентом»** и серверное время ввода/изменения UTC (RFC3339Nano). После входа с ЭЦП ФИО/email могут иметь источник **«сертификат ЭЦП НУЦ РК»**: пустые и прежние сертификатные поля заполняются/обновляются из проверенного сертификата, ручные значения сохраняются. Ручное изменение снимает сертификатный источник; сохранение неизменённого значения сохраняет источник и дату. Это не подтверждение учебных сведений. Неизменённое значение сохраняет прежнюю дату. Для пустого ещё не сохранённого поля нет утверждения об источнике. Нет признака достоверности, зачисления или внешней проверки. Пользователь не задаёт источник, дату, роль или ID владельца через форму.

Создание черновика явно копирует текущие поля профиля вместе с источниками и датами. В заявлении отдельно редактируются эти три поля и текст обращения о предоставлении общежития (до 2000 символов). Изменение профиля не меняет существующие черновики и поданные заявления; изменение заявления не меняет профиль. Неполные черновики разрешены. Для отправки обязательны четыре непустых поля, синтаксически корректный email и явное принятие текущего согласия. Форма показывает сохранённый снимок перед отправкой.

## Статусы и отзыв — проектное предложение

Все шесть локальных статусов являются **проектным предложением, а не утверждённым регламентом**:

| Код | Статус | Реализованное поведение |
| --- | --- | --- |
| draft | черновик | Создание, сохранение неполным, редактирование владельцем |
| submitted | подано | Единственная отправка сохранённого снимка с номером, датой и согласием |
| under_review | на проверке | Назначенный сотрудник проверяет текущие сведения и документы |
| needs_information | требуется дополнение | Запрос дополнения с комментарием, исправления и повторная отправка |
| verified | проверено | Завершена ручная проверка конкретного снимка; не одобрение размещения |
| withdrawn | отозвано | Отзыв владельцем только из submitted |

Предложенное локальное правило отзыва: **студент может отозвать заявление только в статусе «подано», до начала проверки**. Черновик не отзывается. Из «на проверке», «требуется дополнение», «проверено» и «отозвано» отзыв запрещён. После отзыва сохраняются снимок, регистрационный номер/дата, принятое согласие и история; редактирование и повторная отправка этой записи запрещены. Отдельное новое заявление можно создать без ограничений по периоду. Отзыв заявления не означает отзыв согласия на обработку данных: юридический механизм, последствия и хранение требуют Q-22.

Ручные переходы проверки, документы, запрос дополнения и повторная отправка реализованы отдельным расширением; [матрица, история и проверки](application-review.md). История содержит фактические события с автором, временем, статусом и версией. Решений комиссии, ранжирования, очереди, категории, права выбора, брони и заселения нет.

## Регистрация, согласие и повторы

Номер `APP-00000001` образуется из глобального уникального INTEGER PRIMARY KEY AUTOINCREMENT в отдельной таблице регистраций. Номер выдаётся при отправке, не при создании черновика; формат — техническое предложение без ежегодного сброса. Дата регистрации — серверное UTC-время успешной отправки. Не заявляется юридически непрерывная нумерация. Нет ограничений числа заявлений за период и межканального исключения дублей.

Текст согласия хранится в `application_consents`, версия `test-v1`. Заголовок текста: **«ТЕСТОВЫЙ ТЕКСТ — ТРЕБУЕТ СОГЛАСОВАНИЯ»**. Это не утверждённое юридическое основание. Согласие не проставлено заранее. При подаче сохраняются версия, серверная дата принятия и владелец (локальный user_id заявления), связанный с неизменяемым текстом; событие подачи есть в истории и аудите. Карточка поданного/отозванного заявления читает именно принятую версию. Новые тексты добавляются отдельными версиями следующими миграциями; текущая версия приложения меняется явно, старые тексты не редактируются. Перевод самого юридического текста требует отдельного согласования; сейчас тестовый текст хранится на русском и показывается без автоматического перевода.

Каждый черновик получает случайный ключ отправки, привязанный к конкретной записи и владельцу. POST отправляет ключ, ожидаемую версию черновика и версию согласия. Сохранение, принятие согласия, регистрация, история и аудит атомарны в `audit.Recorder.RecordChange`; репозитории и повторная проверка разрешения `AuthorizeTx` используют переданный `*sql.Tx`. Уникальность регистрации подкреплена БД. Повтор **того же** успешно отправленного запроса (в том числе одновременный) возвращает прежнюю карточку/номер, без нового аудита или истории. Это верно и при сетевом повторе после отзыва: состояние остаётся отозванным. Другой ключ, устаревшая редакция или попытка новой отправки отозванной записи дают 409. Непринятое/неактуальное согласие и неполные поля дают 422; данные не меняются. После редактирования старая форма отправки отклоняется с 409.

## Доступ и маршруты

| Маршрут | Методы | Назначение |
| --- | --- | --- |
| `/student/profile` | GET, HEAD, POST | Собственный профиль |
| `/applications` | GET, HEAD | Только собственные заявления |
| `/applications/new` | POST | Создание черновика |
| `/applications/{applicationID}` | GET, HEAD | Карточка и история |
| `/applications/{applicationID}/edit` | GET, HEAD, POST | Черновик и исправления needs_information/verified |
| `/applications/{applicationID}/submit` | POST | Отправка |
| `/applications/{applicationID}/withdraw` | POST | Отзыв |

Все изменяющие маршруты проходят общую CSRF-проверку auth. В сервисе проверяется applications.own, для изменения — повторно внутри транзакции. Область данных — владелец заявления, общежитие не выбирается и не назначается. Каждый SQL-запрос карточки, истории и изменения ограничен локальным actor ID из сессии. Чужой и несуществующий ID одинаково дают 404. Для собственных маршрутов сотрудники и системный администратор не получают обхода доступа (403); отдельные маршруты проверки требуют applications.review и назначения конкретному заявлению; без входа — 401. Конфликт версии или статуса — 409. Персональные поля и ключ отправки не попадают в аудит или технические логи; аудит содержит идентификаторы и коды. С 000009 отдельная закрытая предметная история содержит снимки полей и ссылки на версии файлов; персональные данные не копируются в общий аудит. SQL выполняется только в репозитории, HTML экранируется. Интерфейс и навигация поддерживают RU/KK; пользовательские значения сохраняют исходный язык.
