# SQLite и обязательный аудит

Подключение находится в `internal/platform/database`, используется `database/sql` и существующий драйвер `github.com/mattn/go-sqlite3`. Новых зависимостей не добавлено. `Open(ctx, path)` принимает путь к постоянной БД, создаёт недостающий файл, проверяет подключение и применяет встроенные миграции до запуска HTTP. Новая миграция `000002_audit_events.sql` дополняет существующую историю; первая миграция не изменялась.

## Соединения и миграции

Настройки `_foreign_keys=on`, `_journal_mode=WAL`, `_synchronous=FULL`, `_busy_timeout=5000` и `_txlock=immediate` передаются в DSN. Драйвер применяет их при открытии каждого физического соединения, поэтому внешние ключи не зависят от того, какое соединение выбрал `database/sql`. В пуле явно заданы максимум 1 открытое и 1 простаивающее соединение; `ConnMaxLifetime` и `ConnMaxIdleTime` равны 0. Приложение рассчитано на один экземпляр и постоянное локальное хранилище.

Нумерация SQL-миграций непрерывна, начиная с `000001`. `schema_migrations` хранит имя, SHA-256 и время применения. Новые миграции и записи их журнала сохраняются в одной транзакции. При повторном запуске проверяются история и контрольные суммы; изменённая, пропущенная или неизвестная применённая миграция вызывает ошибку. При ошибке SQL новые изменения откатываются. Понижение версии БД автоматически не выполняется.

`context.Context` передаётся в `PingContext`, `BeginTx`, `ExecContext`, `QueryContext` и `QueryRowContext`. Таймаут занятой БД ограничен отдельно: SQLite может ждать занятый ресурс до 5 секунд, даже если контекст истёк раньше. Ожидание свободного соединения пула отменяется контекстом. Длительность операции нужно выбирать с учётом обоих ограничений. Автоматического повторения транзакций нет.

## Минимальное событие аудита

| Поле таблицы | Содержание |
| --- | --- |
| `id` | Внутренний целочисленный ключ события. |
| `actor_id` | Непустой идентификатор доверенного сотрудника или системного исполнителя. Поле не заменяет проверку полномочий. |
| `occurred_at` | Время вставки в UTC, устанавливаемое SQLite. Это время записи события, не дата вступления бизнес-решения в силу. |
| `action` | Непустой короткий код действия. |
| `object_type`, `object_id` | Тип объекта и его постоянный идентификатор. |
| `result` | Непустой короткий код результата без текста исключений или содержимого документов. |
| `request_id` | Непустой идентификатор запроса или фоновой операции. |

Для поиска созданы индексы по объекту и `request_id`. Действия и результаты определяются будущим вызывающим модулем; эта основа не вводит правила размещения. Ссылки на автора и объект не являются внешними ключами: автором может быть локальный ID из auth_users или служебный исполнитель, а object_id остаётся полиморфной ссылкой на предметный объект. Inventory добавил отдельную защищённую внешним ключом ссылку dormitory_id на общежитие. Фактическая работа внешних ключей проверяется на связанных тестовых таблицах, без выдуманной схемы фонда или пользователей.

`Event` не содержит произвольного payload, анкеты или тела документа. В поля передаются идентификаторы и коды, а не ФИО, пароли, токены или сообщения ошибок. Основания и изменения статусов мест по 1.7 хранятся в закрытой `inventory_bed_history` атомарно с местом и аудитом; общий интерфейс аудита, production-полномочия, сроки хранения и защита от изменения журнала ещё требуют реализации и согласования по Q-07 и Q-08. Наличие таблицы не означает защищённый от владельца файла БД журнал.

## Транзакционный контракт

Для связанных изменений без обязательного бизнес-аудита используется `database.WithinTx(ctx, db, callback)`. Для деловых изменений с обязательным аудитом используется `audit.NewRecorder(db).RecordChange(ctx, callback)`; зависимости создаются конструкторами при подключении реального бизнес-модуля в `internal/app`.

Контракт callback в `RecordChange`:

```go
func(context.Context, *sql.Tx) (audit.Event, error)
```

1. Вызывающий модуль передаёт контекст операции. Для HTTP middleware уже создал серверный ID и поместил его в контекст через `requestid.WithID`. Для фоновой операции ID задаётся явно через этот же механизм или поле события.
2. Внутри callback связанные репозитории используют только полученный `*sql.Tx` и контекст. SQL находится в репозиториях. Обращение к исходному `*sql.DB` внутри callback не входит в транзакцию и при пуле из одного соединения может заблокировать собственную операцию. Вложенных транзакций нет.
3. Callback возвращает событие после успешного делового изменения, когда известен ID объекта. `actor_id` поступает из доверенной идентификации, а не из поля формы или заголовка. Если `Event.RequestID` пуст, Recorder берёт его из контекста. Отсутствие обязательного поля приводит к откату.
4. Recorder записывает событие параметризованным `INSERT` через тот же `*sql.Tx`, затем выполняется общий `COMMIT`. Отдельного публичного метода записи обязательного аудита после фиксации изменения нет.
5. При ошибке изменения, вставки аудита или `COMMIT`, отмене контекста либо панике откатывается вся транзакция. Callback не должен сам вызывать `Commit` или `Rollback`. Паника после отката передаётся вызывающему коду. Исходные ошибки сохраняются для `errors.Is` и `errors.As`; значения событий не журналируются.

Откатившаяся операция не оставляет события об успехе. Автоматической отдельной записи неуспешных попыток вне деловой транзакции сейчас нет. Для такого аудита необходим отдельный согласованный сценарий; обязательный аудит успешного изменения нельзя заменять техническим сообщением.

## Технические логи и проверка

Middleware создаёт новый ID, игнорируя входящий `X-Request-ID`, передаёт его в контекст и ответ. Техническая запись содержит ID, нормализованный HTTP-метод, шаблон маршрута, статус и длительность. Неизвестный маршрут обозначается `unmatched`; сырой путь, query string, заголовки, тело запроса и значение паники не выводятся. При панике остаётся стек без её значения. Произвольные строки ошибок, содержащие пользовательские данные, нельзя добавлять в технические логи.

Команды проверки из корня:

```sh
go test ./...
go vet ./...
go build -o bin/server ./cmd/server
```

Тесты создания, повторного запуска и обновления БД находятся в `internal/platform/database/database_test.go`. Там же проверяются реальные нарушения внешних ключей на разных и заменённых соединениях, WAL, таймаут и освобождение ресурсов после конфликта. `internal/modules/audit/service_test.go` проверяет совместную фиксацию, откат по ошибке бизнеса и аудита, отказ фиксации, отмену и панику. `internal/platform/httpserver/middleware_test.go` проверяет корреляцию и отсутствие тестовых секретов в логах, включая случай паники. Все БД создаются во временных каталогах.

Миграция inventory расширила audit_events полями `dormitory_id` и `changes_json`: разрешённые серверные снимки полей фонда до/после изменения сохраняются вместе с основным событием. Это деловые данные в БД, а не технический лог; пароли, токены, тела документов и анкеты в такие снимки не включаются. Подробности — в [inventory.md](inventory.md).

Для согласованности с удалением фотографий включён `synchronous=FULL` на каждом соединении: успешный COMMIT метаданных должен стать долговечным до удаления файла. Режим проверяется также на заменённых соединениях. Контракт файлов и восстановления — в [photos.md](photos.md).

Миграция `000007_registry_export.sql` добавляет индекс истории по общежитию/времени и триггеры, запрещающие UPDATE/DELETE audit_events. INSERT через RecordChange сохранён. Scoped-просмотр истории реестра, транзакционная проверка прав отчётов и проверки неизменяемости описаны в [reports.md](reports.md). Запрет через приложение не защищает от владельца файла БД, способного удалить триггеры; политика хранения и эксплуатационная защита остаются отдельными решениями.

Команда backup удерживает BEGIN IMMEDIATE на отдельном соединении и создаёт VACUUM INTO через другое read-only-соединение: снимок включает зафиксированные WAL-записи и совпадает с копируемыми связанными фото. На основном файле не используется immutable=1, WAL вручную не удаляется. Перед/после проверяются integrity_check и foreign_key_check; [контракт и тесты](backup.md).

Расширение applications 000009 сохраняет изменение, версии документов/результаты ручной проверки, закрытые предметные снимки, уведомление и аудит через RecordChange в одном tx. Комментарии/анкеты/байты не входят в payload аудита. Новая версия файла синхронизируется до COMMIT метаданных; сверка documents использует ту же блокировку и отдельное пространство ключей. При ошибке обязательной истории/уведомления/аудита действие откатывается, бесхозный файл очищается. Тесты отказов и восстановления — [application-review.md](application-review.md).
