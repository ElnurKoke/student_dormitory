# Реестр жилого фонда

Модуль `internal/modules/inventory` реализует общежития, корпуса, этажи, комнаты и койко-места. Для каждого уровня есть список, карточка, создание, редактирование, архивирование и восстановление. Фотографии общежитий и комнат добавлены; контракт и проверки — в [photos.md](photos.md). Публичный каталог добавлен на основе отдельной модели inventory; [контракт и проверки](catalog.md). Статистика ещё не добавлена.

## Структура и запуск

`handler.go` разбирает HTTP и формирует представления, `service.go` проверяет полномочия и правила, `repository.go` выполняет параметризованный SQL. Модель и проверка полей не зависят от HTTP. Зависимости передаются конструкторами из `internal/app`. Используются существующие Go, SQLite, серверные шаблоны, CSS, auth и аудит; новых зависимостей нет.

Миграция `000004_inventory.sql` добавляет четыре связанные таблицы и расширяет `audit_events` полями общежития и изменений. Миграция `000005_inventory_beds.sql` добавляет места, историю и ограничения вместимости. Старые миграции не меняются. При запуске сервер применит новую миграцию автоматически:

```sh
go test ./...
go vet ./...
go build -o bin/server ./cmd/server
APP_ENV=development DEV_LOGIN_ENABLED=true ./bin/server
```

Для новой development-БД сначала создайте пользователей отдельной командой, как описано в [auth.md](auth.md). Сервер не создаёт пользователей или фиктивные объекты фонда автоматически. Корневой список: `/staff/dormitories`. На карточке родителя находится список его дочерних объектов и кнопка добавления. Административные списки по умолчанию включают архив; фильтры позволяют явно выбрать активные или архивные записи.

## Данные и постоянные связи

| Объект | Поля |
| --- | --- |
| Общежитие | Постоянный ID, название, адрес, собственник или оператор, основание использования, контакты, описание, признак публикации. |
| Корпус | Постоянный ID, ссылка на общежитие, название. |
| Этаж | Постоянный ID, ссылка на корпус, номер. Номер — строка, чтобы поддержать, например, цокольный уровень. |
| Комната | Постоянный ID, ссылка на этаж, номер, вместимость, площадь, оснащение, санитарно-бытовые условия, признак доступности и пояснение, стоимость, валюта и период. |
| Койко-место | Постоянный ID, неизменяемая ссылка на комнату, обозначение до 64 символов, статус. |

У каждого объекта есть признак архива, версия и время обновления UTC. Идентификаторы корпуса, этажа, комнаты и места генерируются сервером. ID общежития берётся из заранее назначенного пользователю набора ID; после создания он также неизменяем. ID `new` зарезервирован маршрутом создания и не допускается. Триггеры запрещают изменение первичных ID в SQLite. Формы не меняют родителей, а сервис проверяет всю цепочку вложенных ID по реальным связям БД.

Связи общежитие → корпус → этаж → комната → койко-место защищены внешними ключами с `ON DELETE RESTRICT` и `ON UPDATE RESTRICT`. Номер комнаты после обрезания краевых пробелов уникален внутри этажа, включая архивные комнаты. Та же строка номера на другом этаже допустима. Сравнение номеров точное, без приведения регистра или числового преобразования; дополнительные правила нумерации пока не утверждены. Обозначение места также уникально внутри комнаты, включая архив; другие названия и номера не объявлены уникальными.

## Создание общежитий и права

Для чтения требуется `registry.read`, для создания, редактирования, архива и восстановления — одновременно `registry.read` и `registry.write`. Для смены статуса места нужны `registry.read` и отдельное `places.status.write`. Все операции требуют назначения целевого общежития. Сотрудник не создаёт произвольный новый ID с автоматическим расширением своих полномочий. Форма создания общежития предлагает только уже назначенные ID, для которых ещё нет записи в реестре. Например, назначение `dev-dorm-1` из команды dev-users позволяет внести реальное описание этого объекта.

`auth_user_dormitories` поэтому сохраняет возможность предварительного назначения ID до появления записи в фонде. Такие ID не считаются созданными общежитиями, не попадают в список существующих объектов и не порождают фиктивные данные. Если назначенный объект ещё не внесён, ссылка сотрудника с правом записи ведёт на форму создания. Отдельный интерфейс управления назначениями не входит в этот шаг.

Права проверяются в сервисе для списка, просмотра, форм и изменений. Для записи они повторно проверяются через тот же `*sql.Tx`, что и деловое изменение. Подмена ID общежития, корпуса, этажа или комнаты не меняет принадлежность записи. Комендант в текущей тестовой матрице читает назначенный фонд и меняет статусы мест, но не создаёт и не редактирует характеристики объектов. Сотрудник реестра создаёт и редактирует объекты, но без дополнительного права статусы не меняет. Администрация читает фонд. Студент и системный администратор доступа к фонду не имеют. Скрытие кнопки не заменяет проверку прямого GET/POST.

Все изменяющие формы проходят общую CSRF-защиту. Лимит тела форм увеличен до 64 KiB для текстовых характеристик; длины отдельных полей дополнительно ограничиваются сервисом. Actor ID берётся из серверной сессии, а не из формы.

## Проверка полей и стоимость

Название, адрес, собственник/оператор, основание и контакты общежития обязательны. Описание необязательно. Название корпуса и номер этажа обязательны. Для комнаты обязательны номер, положительная целая вместимость, положительная площадь, оснащение, санитарно-бытовые условия, стоимость, валюта и период. Для отсутствующего оснащения можно явно указать «Нет». Пояснение доступности необязательно; снятый флажок означает, что комната не отмечена как доступная, а не проведённую проверку нормативного соответствия.

Текст обрезается по краям и ограничивается по длине: название 200, номер 64, адрес 500, оператор 300, основание 500, контакты 1000, описание 2000, оснащение/санитарные условия/пояснение доступности по 1000 символов. Длинные значения не обрезаются молча: возвращается ошибка поля. При ошибке форма сохраняет введённые значения.

Деньги хранятся в `price_minor` как неотрицательный SQLite INTEGER/int64. В форме вводится целое число минимальных денежных единиц без float, экспоненты и скрытого умножения на 100. Код валюты обязателен: три латинские буквы, сохраняется в верхнем регистре. Полный справочник валют не реализован. Период — обязательная строка до 64 символов, например «месяц»; это явная характеристика стоимости, не правило начисления. Конвертация, платежи, тарифный расчёт и финансовые интеграции не добавлены.

Площадь хранится отдельно как целое число сотых долей м². Форма принимает точку или запятую и до двух дробных знаков. Вместимость, площадь и сумма проверяются на переполнение. Точность стоимости сохраняется и для целых чисел больше `2^53`.

## Архивирование и удаление

Архивирование не удаляет строки, не меняет ID, родительские ссылки или характеристики. Флаг публикации хранится отдельно и при архивировании не переписывается; публичный каталог учитывает активность всей фактической цепочки, а не только этот флаг.

Родителя нельзя архивировать, если в его поддереве есть активные объекты. Порядок явный: койко-места, комнаты, этажи, корпуса, общежитие. После этого все записи и связи по-прежнему доступны в административном просмотре и списках с архивом. Восстановление идёт в обратном порядке: родитель должен быть активен. Каскадного архивирования, скрытого восстановления и автоматического перемещения нет. Редактирование и создание дочерних объектов запрещены, если объект или любой его родитель архивирован.

Физического удаления в административных страницах и маршрутах нет. DELETE известного объекта возвращает 405. Дополнительно SQLite не позволяет удалить родителя с существующими дочерними ссылками, даже если дети архивированы. Ссылка аудита на общежитие также защищена внешним ключом. Места и их история защищают связанные комнаты и пользователей от удаления; история не удаляется при архивировании.

## Транзакции и аудит

Создание, изменение, архивирование и восстановление выполняются через `audit.Recorder.RecordChange`. В одной транзакции происходят повторная проверка прав, проверка актуального состояния родителей и версии, запись объекта и обязательная запись аудита. Ошибка любого шага откатывает всё. `version` защищает от потерянных изменений: устаревшая форма получает 409 и ссылку на актуальную форму, а введённые значения не теряются молча.

Событие содержит локальный ID автора, время, действие, тип и постоянный ID объекта, результат, request_id, ID общежития и серверные снимки разрешённых полей до/после в `changes_json`. Произвольное тело формы, пароли, токены, документы и анкеты в снимки не включаются. Контактные сведения оператора являются частью деловой записи; эти снимки не выводятся в технические логи. UI просмотра общего журнала и его политика хранения остаются отдельной работой.

## Койко-места и статусы

На карточке комнаты отображаются места и их текущие статусы. Место создаётся свободным; обозначение обрезается по краям и сравнивается точно, без изменения регистра. Оно уникально внутри комнаты, включая архив. На другой комнате такое же обозначение допустимо. ID и комната неизменяемы, в том числе на уровне SQLite.

Схема и предметная модель предусматривают пять статусов:

| Код | Название | Допустимые ручные назначения из этого состояния |
| --- | --- | --- |
| `free` | Свободно | `maintenance`, `unavailable` |
| `maintenance` | На ремонте | `free` |
| `unavailable` | Временно недоступно | `free` |
| `reserved` | Забронировано | Нет |
| `occupied` | Занято | Нет |

Эта матрица задана запросом пользователя от 15.11.2026 (частичный ответ Q-04). Она проверяется сервисом, включая прямые запросы. Повтор того же статуса и любые другие переходы отклоняются с 422. Создание и редактирование обозначения не принимают статус из формы. Значения `reserved` и `occupied` предназначены для будущих процессов бронирования и заселения; ручных операций их назначения нет. Архивирование этих двух будущих состояний также недоступно, чтобы административный архив не выводил их из учёта.

Для каждого изменения места (включая создание, обозначение, архив и восстановление) обязательно текстовое основание от 1 до 1000 символов после обрезания краевых пробелов. Это реквизиты внешнего основания, без загрузки файла и проверки его подлинности. Автор берётся из серверной сессии, время UTC назначает БД. В `inventory_bed_history` хранятся версия, действие, предыдущий и новый статусы, основание, автор и время. У создания предыдущий статус отсутствует; при смене обозначения или архива статус сохраняется. История видна на закрытой карточке места по тем же правам `registry.read` и назначению общежития. Это не интерфейс общего аудита.

Запись места, история и `audit_events` сохраняются атомарно через `RecordChange` с повторной проверкой прав `AuthorizeTx` и всей цепочки родителей. Аудит содержит снимки до/после и ID строки истории; свободный текст основания остаётся только в закрытой истории и не выводится в технический журнал. Ошибка истории, аудита или фиксации откатывает всё.

Статус, обозначение и архив используют одну версию места. Обновление выполняется с условием на ожидаемую версию, смена статуса дополнительно проверяет прежний статус. Из двух запросов с одной версией сохраняется только один; второй получает 409. Форма конфликта сохраняет основание и исходную версию, предлагает явно загрузить актуальные данные; автоматического повтора или перезаписи нет. SQLite использует существующие `BEGIN IMMEDIATE` и `busy_timeout`.

Вместимость ограничивает число всех неархивных мест, независимо от статуса. Ремонт и временная недоступность не освобождают слот. Создание и восстановление проверяют вместимость внутри транзакции; уменьшение вместимости ниже числа действующих мест возвращает ошибку поля. SQLite-триггеры дополнительно защищают вставку, восстановление и уменьшение вместимости. Архив сохраняет место, обозначение и историю; восстановление требует активных родителей и свободной вместимости. Комнату с действующими местами архивировать нельзя, каскада нет.

Маршруты места продолжают полную вложенность: `/staff/dormitories/{dormitoryID}/buildings/{buildingID}/floors/{floorID}/rooms/{roomID}/beds/new`, `/beds/{bedID}`, `/edit`, `/archive`, `/restore`, `/status`. `/status` поддерживает GET/HEAD формы и POST изменения. Все POST защищены общей CSRF-защитой.

`internal/modules/inventory/bed_test.go` проверяет всю матрицу переходов (включая будущие состояния), обязательность основания, неизменяемость ID/родителя, атомарный откат при ошибках истории и аудита, конфликт двух одновременных смен статуса, гонки создания мест и уменьшения вместимости, архив/восстановление, ограничения БД, назначения и повторную проверку прав в транзакции. `internal/app/bed_test.go` проверяет формы и историю, допустимые опции, прямые запрещённые запросы, CSRF, безопасный вывод основания, доверенные авторство/время, конфликт 409, вместимость, роли и отзыв назначения.
