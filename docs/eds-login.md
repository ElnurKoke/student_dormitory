# Вход с ЭЦП через NCALayer и NCANode

Расширение по запросу пользователя от 16.11.2026: вход без логина/пароля для всех ролей, автоматическая регистрация неизвестного ИИН и заполнение кабинета из проверенного сертификата. Клиент работает с модулем `kz.gov.pki.knca.basics` NCALayer, сервер — с приватным NCANode API v3 (`/cms/verify`, `/cms/extract`). SDK, контейнер и пользовательские ключи в репозиторий не включены.

## Настройка

На компьютере пользователя установите и запустите [NCALayer с официального сайта НУЦ РК](https://pki.gov.kz/ru/ncalayer/). Пароль ключа вводится только в его окне. Браузеру может понадобиться разрешение доступа к локальной сети.

На сервере приложения нужен **свой доверенный NCANode**, с актуальными доверенными сертификатами НУЦ РК и доступом к OCSP. Публичный демонстрационный сервер не используется. NCANode — отдельный проект, не сам NCALayer и не сервис этого Go-приложения. Его [официальный README](https://github.com/ncanode-kz/NCANode) описывает установку, SDK Kalkan и Docker. В репозитории подготовлен `compose.ncanode.yaml` для NCANode 3.5.1. Образ разработчика зафиксирован digest `sha256:052222f30ac73d9f0060a5c80c572723d25dd84e21073435795a10db254c02b8`, поддерживает amd64/arm64. Контейнер не получает файлы приложения и ключи; используется только отдельный Docker-том кеша. Порт привязан к `127.0.0.1:14579`, перезапуск — `unless-stopped`, есть healthcheck. Отладочные ответы, трассировка и журнал самого NCANode выключены; приложение продолжает вести технический журнал и обязательный бизнес-аудит без чувствительного payload.

Запустите Docker Desktop, затем из корня проекта:

```sh
docker compose -f compose.ncanode.yaml up -d --wait
docker compose -f compose.ncanode.yaml ps
```

Остановка без удаления кеша:

```sh
docker compose -f compose.ncanode.yaml stop
```

Проверяйте версию образа и контракт перед эксплуатацией: адаптер принимает отчёт API v3 с `status: 200`, `valid: true`, ровно одним подписантом со `status: VALID`, одним элементом `certificates`, его сроками/`valid`/`subject`/`keyUsage` и явным успешным OCSP. Старый JSON-RPC API v1/v2 и ответы без результата этих проверок не принимаются. [OpenAPI](https://github.com/ncanode-kz/NCANode/blob/master/openapi.yml), [реальная реализация CMS](https://github.com/ncanode-kz/NCANode/blob/master/src/main/java/kz/ncanode/service/CmsService.java) и [DTO подписанта](https://github.com/ncanode-kz/NCANode/blob/master/src/main/java/kz/ncanode/dto/cms/CmsSignerInfo.java) задают используемый контракт.

В закрытом `.env` задайте `NCANODE_URL=http://127.0.0.1:14579`, `EDS_ORIGIN=http://localhost:8080` и остальные текущие настройки. Файл не коммитится. Запуск `./scripts/run-local.sh` загружает его, собирает актуальный бинарник и запускает сайт; изменения настроек требуют перезапуска. Прямой `go run ./cmd/server` по-прежнему не загружает `.env` автоматически.

Альтернатива — явное окружение Go-сервера:

```sh
DEV_LOGIN_ENABLED=false \
NCANODE_URL=http://127.0.0.1:14579 \
EDS_ORIGIN=http://localhost:8080 \
go run ./cmd/server
```

Откройте `/auth/login`. Для production задайте `APP_ENV=production` и `EDS_ORIGIN=https://ваш-домен` без пути и завершающего `/`, обслуживайте сайт по HTTPS. `NCANODE_URL` допускает HTTPS либо HTTP на loopback; логин/пароль в URL, путь, query и fragment запрещены. Адрес не берётся из формы или proxy-заголовков. Перенаправления проверяющего сервиса запрещены; TLS проверяется стандартным клиентом, переменные HTTP proxy для запросов ЭЦП не используются. Сертификат/подпись не отправляются стороннему облаку.

Пустой `NCANODE_URL` выключает ЭЦП-вход и приём NCA-сессий. В development с включённым тестовым входом видна явная пометка, что ЭЦП не настроена. Если оба способа выключены, `/auth/login` отсутствует, как и раньше. Development-пароли остаются только при `APP_ENV=development DEV_LOGIN_ENABLED=true`; в production такой режим запрещён.

## Первое назначение и существующие сотрудники

Автоматически новый ИИН получает только `student`. Должность, организация, тип сертификата, его текстовые поля и данные формы не назначают административные роли. Затем роли меняются системным администратором через `/admin/users` по [контракту auth](auth.md).

Для **первого** администратора на новой БД: остановите сервер, создайте закрытый файл `var/admin-iin.txt` с его 12 цифрами ИИН, установите права `0600`, затем выполните:

```sh
go run ./cmd/eds-account -iin-file var/admin-iin.txt -bootstrap-admin
```

Команда создаёт локальный ID, привязку NCA и роль `system_admin` с аудитом. Она отказывает, если уже есть активный системный администратор или этот ИИН уже привязан. Имя заменяется данными сертификата при первом проверенном входе; до этого сертификат не считается проверенным. Пароль не создаётся. После команды запустите сервер с настройками NCANode выше.

Для существующего сотрудника/администратора узнайте его **постоянный локальный ID** в учётных записях, сохраните его ИИН в закрытом файле, остановите сервер и выполните:

```sh
go run ./cmd/eds-account -iin-file var/staff-iin.txt -user-id EXISTING_LOCAL_ID
```

Команда работает и в production под оператором сервера; ИИН не передаётся в аргументах процесса и не печатается. ID, роли, назначения, состояние enabled, пароли, заявления и история сохраняются. Повтор той же привязки идемпотентен. Нельзя перепривязать ИИН к другому аккаунту или привязать второй ИИН тому же аккаунту; автоматического слияния по ФИО/email нет. Общая maintenance-блокировка не допускает одновременную работу команды и сервера. Все изменения и аудит атомарны. Отключённый аккаунт можно связать, но вход в него запрещён; автоматическая регистрация не обходит блокировку.

Привязку существующих сотрудников нужно сделать до их первого входа с ЭЦП: иначе неизвестный ИИН по требуемому сценарию создаст отдельного студента. Команда не перезаписывает существующие связи и не является обходом проверки подписи.

## Сценарий пользователя

1. Страница проверяет WSS-подключение к `127.0.0.1:13579` и приветствие NCALayer; показывает «NCALayer запущен» либо инструкцию запуска/разрешения браузера. Можно повторить проверку.
2. «Войти с ЭЦП» запрашивает одноразовый challenge через POST с CSRF. Срок — не более 5 минут и оставшегося срока анонимной сессии.
3. NCALayer предлагает доступные хранилища и пароль ключа. Сайт не читает файл ключа и пароль. Подписывается CMS с вложенными данными, без предварительного хеширования и без TSP.
4. Сервер проверяет подпись через NCANode, текущие сроки сертификата, доверие, OCSP и точное совпадение вложенного содержимого с серверным challenge.
5. По проверенному ИИН находит связанный аккаунт либо создаёт студента. После атомарной фиксации выдаёт новый cookie и открывает `/account`.

Отмена, обрыв WSS, запрет локальной сети, неподходящий/недействительный сертификат и недоступный NCANode показывают понятную ошибку с возможностью повторить вход. Подтверждение доступности NCALayer само по себе не авторизует пользователя. Неподдерживаемый ответ, неопределённая проверка или отсутствие OCSP не разрешают вход.

## Данные и транзакции

Постоянный случайный `auth_users.id` сохраняется отдельно от `(provider='nca', subject=ИИН)` в `auth_external_identities`; уникальны и ИИН, и пользователь для NCA. Перевыпуск сертификата с тем же ИИН не создаёт нового аккаунта. Полный сертификат, CMS, пароль и закрытый ключ в БД не сохраняются. ИИН — персональные данные, он хранится только в закрытой БД и выводится владельцу в кабинете и собственном профиле, не в каталоге, списке пользователей, аудите или технических логах.

`auth_certificate_profiles` содержит последнее проверенное ФИО (`CN` и дополнительное имя из `G`, если присутствует и ещё не входит в `CN`), email при наличии и серверное время проверки. Отсутствующий email не мешает входу и не выдумывается; для подачи заявления его надо заполнить. Проверенный email из сертификата не равен подтверждению текущего владения почтовым ящиком. Учебная группа и сведения о зачислении из сертификата не выводятся.

Для студента явный контракт `applications.SeedCertificateProfileTx` заполняет пустые ФИО/email либо обновляет прежние значения с источником «сертификат ЭЦП НУЦ РК». Значения, уже введённые вручную, не перезаписываются. Неизменённые поля сохраняют источник и дату при сохранении формы; ручное изменение получает источник «введено студентом». Группа остаётся ручным полем. Существующие заявления хранят отдельные снимки и не переписываются при входе или обновлении сертификата. У сотрудников отдельный профиль заявлений этим не создаётся.

Challenge содержит назначение `student_dormitory.login`, настроенный origin, криптографический nonce и срок. Он связан с анонимной серверной сессией; новый challenge заменяет прежний. Проверка сети выполняется до блокировки SQLite, затем сессия, содержимое и срок повторно проверяются внутри транзакции. Успешный вход удаляет прежнюю сессию и challenge, создаёт новые session/CSRF, сохраняет пользователя/идентичность/профиль и обязательный аудит через `RecordChange`. Ошибка любого обязательного элемента откатывает всё. Параллельные входы одного ИИН создают один локальный аккаунт. Повтор использованного запроса не создаёт сессию.

Аудит: `auth.eds_challenge_created`, `auth.eds_registered` либо `auth.login`, а для команды — `auth.nca_identity_linked`/`auth.nca_admin_bootstrapped`. События содержат только локальные ID и коды; регистрация и вход нового пользователя представлены одним событием регистрации. ИИН, ФИО, email, CMS, nonce, certificate subject и ошибки проверяющего сервиса не попадают в аудит или технический журнал. Настройки журналирования самого NCANode также должны исключать тела запросов/ответов и полные сертификаты; это отдельный процесс.

Production-cookie остаётся `__Host-dorm_session` с Secure, HttpOnly и SameSite=Lax. Все изменяющие маршруты проходят общую CSRF-защиту. CSP разрешает соединение с NCALayer только странице входа; весь клиентский JS выдаётся локально без CDN. Ответы входа/кабинета/проверки не кешируются. Лимиты: CMS до 32 КиБ Base64, обычный POST до 64 КиБ, ответ NCANode до 1 МиБ, суммарная проверка NCANode до 20 секунд. Клиент ждёт ответ окна подписи до 3 минут и сетевой POST до 30 секунд.

Все БД и API-подстановки тестовые; рабочие пользователи/файлы не изменялись. Проверка настоящей ЭЦП остаётся отдельным пунктом выше.

Compose-проект `student-dormitory-nca`, контейнер `student-dormitory-ncanode`, том `student-dormitory-nca_ncanode_cache`. Проверено `healthy`, `restart=unless-stopped`, публикация только `127.0.0.1:14579`. `/actuator/health`, компоненты `ca` и `crl` возвращают `UP`. Реальный OpenAPI подтвердил используемые поля CMS/сертификата и наличие `/cms/verify`/`/cms/extract`.

Создан закрытый локальный `.env` (`0600`, исключён из Git) с `NCANODE_URL=http://127.0.0.1:14579` и `EDS_ORIGIN=http://localhost:8080`. Работающий сайт корректно перезапущен через `scripts/run-local.sh`; прежние `APP_ENV=development`, `DEV_LOGIN_ENABLED=true`, адрес `127.0.0.1:8080`, БД и хранилище сохранены. Контроль локальных ID, enabled, ролей и назначений до/после подтвердил отсутствие изменений.

Проверен настоящий путь `/auth/login` → POST challenge → подпись временным **недоверенным самоподписанным RSA-сертификатом** → POST входа → реальный NCANode: сайт вернул `401`, аккаунт не создан, `/healthz` остался `ok`. Проверочные ключи создавались только во временной папке и удалены; пользовательские ключи не использовались. Положительный вход действительным сертификатом НУЦ РК и его OCSP-результат ещё должен проверить владелец в NCALayer. Наличие UP и отрицательный тест не объявляются таким положительным прогоном.

Повторный запуск после остановки: запустить Docker Desktop, `docker compose -f compose.ncanode.yaml up -d --wait`, затем `./scripts/run-local.sh`. Прямой запуск Go без загрузки окружения не использует `.env`. Обязательные `gofmt`, `go test ./...`, `go vet ./...`, сборка `bin/server`, проверка shell-синтаксиса и Compose выполнены успешно.


## Исправление выбора ключа 16.11.2026

В запросе `kz.gov.pki.knca.basics.sign` добавлен обязательный `signerParams.extKeyUsageOids: []`. Пустой массив разрешает выбор действующих сертификатов без ограничения одним EKU; параметр `chain` не передаётся, поэтому штатная проверка цепочки NCALayer не отключается. Прежний пустой `signerParams: {}` не соответствовал [официальному протоколу НУЦ РК](https://github.com/pkigovkz/sdkinfo/wiki/KNCA-Basics-Module) и мог завершаться ошибкой до появления окна выбора файла/пароля. Клиентский регрессионный тест теперь моделирует отказ NCALayer при отсутствии обязательного массива. Файл ключа и пароль по-прежнему выбираются/вводятся только в NCALayer.

После исправления выполнены семь клиентских регрессионных проверок, полный `go test ./...`, `go vet ./...` и сборка `bin/server`. Локальный сервер пересобран и перезапущен, в браузере загружен обновлённый скрипт. Проверка реального запроса перешла к ожиданию выбора хранилища/пароля; положительный вход пользовательским ключом по-прежнему не заявляется без завершения владельцем.

При повторной проверке выявлена истёкшая анонимная сессия страницы: общий CSRF middleware возвращал HTML 401 на запрос challenge, а клиент показывал общую сетевую ошибку. Клиент теперь один раз загружает обычную страницу входа, получает свежие cookie/CSRF и повторяет только получение challenge до выбора ключа. На истечение сессии после подписи выводится отдельное сообщение; подпись не воспроизводится автоматически. Регрессионные проверки покрывают оба случая.

Итог после обоих исправлений: девять клиентских тестов, полный `go test ./...`, `go vet ./...` и сборка прошли; сервер перезапущен, страница браузера обновлена и показывает «NCALayer запущен». Ввод пользовательского ключа/пароля и положительная криптографическая проверка владельцем не выполнялись агентом.


## Исправление формата CMS 17.11.2026

`kz.gov.pki.knca.basics.sign` возвращает CMS в PEM (`-----BEGIN CMS-----`), что также подтверждено [разъяснением НУЦ РК](https://forum.pki.gov.kz/t/vopros-po-kz-gov-pki-knca-basics/2205). Ранее адаптер ожидал только Base64 DER и отклонял такой ответ до обращения к NCANode. Добавлено преобразование одного PEM-блока CMS/PKCS7 в канонический Base64 DER; обычный Base64 и переносы CR/LF тоже приводятся к канонической строке. Байты подписанного CMS не меняются. Частные ключи, сертификат вместо подписи, несколько блоков, лишний текст, некорректное обрамление, заголовки шифрования и превышение лимита отклоняются.

Нормализация не авторизует запрос: подпись, доверие, сроки, OCSP, ИИН и совпадение содержимого challenge по-прежнему проверяются. `signature_test.go` проверяет сохранность байтов и отказ недоверенной подписи после снятия PEM; `internal/app/eds_test.go` передаёт PEM в сценарии регистрации через HTTP-адаптер и тестовый API. Пользовательские сертификаты/ключи для этих тестов не читаются и не журналируются.

Проверки исправления PEM от 17.11.2026: `gofmt -w cmd internal migrations web`, полный `go test ./...`, `go vet ./...`, сборка и девять браузерных unit-тестов прошли. Локальный сайт перезапущен с новым адаптером. Результат повторного входа действительным ключом должен быть подтверждён владельцем; успешная регистрация на тестовом API не подменяет эту проверку.
