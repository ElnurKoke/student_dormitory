# Сайт студенческих общежитий

Инфраструктурная основа модульного монолита на Go, SQLite, серверных HTML-шаблонах и CSS. Сервер по умолчанию слушает `localhost:8080`, применяет миграции при запуске и завершает активные запросы по SIGINT или SIGTERM перед закрытием БД.

Реализована минимальная основа `audit_events` с атомарной записью делового изменения и его аудита. Добавлен auth: пользователи, роли, разрешения, ограничения общежитиями, серверные сессии и CSRF. Добавлен inventory: общежития, корпуса, этажи, комнаты и койко-места с административными формами, архивом и аудитом. Добавлены фотографии общежитий и комнат: загрузка, описание, порядок, основная и удаление. Публичный каталог использует реальные данные inventory, отдельную публичную модель, фильтры и пагинацию. Добавлены русский и казахский интерфейсы общих, публичных и административных страниц. Добавлены закрытая статистика реестра, CSV-экспорт с фильтрами и история изменений назначенных общежитий. Общий журнал событий без привязки к фонду остаётся отдельным объёмом. Границы продукта — в [docs/mvp.md](docs/mvp.md), исходные коды — в [docs/requirements.md](docs/requirements.md), открытые правила — в [docs/open-questions.md](docs/open-questions.md). Правила разработки — в [AGENTS.md](AGENTS.md).

## Требования к среде

- Go 1.26 или новее.
- `CGO_ENABLED=1` и C-компилятор: [`github.com/mattn/go-sqlite3`](https://github.com/mattn/go-sqlite3) использует CGO. На macOS подходит Clang из Xcode Command Line Tools, на Linux — GCC или Clang. Для межпроцессных блокировок и maintenance-команд поддерживаются macOS и Linux на локальном диске. SQLite включён в драйвер, отдельный сервер БД и утилита `sqlite3` не нужны.

Исходных зависимостей не было. Используются `github.com/mattn/go-sqlite3 v1.14.32` и официальный [декодер WebP](https://pkg.go.dev/golang.org/x/image/webp) из `golang.org/x/image v0.48.0`; остальное использует стандартную библиотеку Go. Версии и контрольные суммы зафиксированы в `go.mod` и `go.sum`.

## Запуск

Из корня репозитория:

```sh
go mod download
go run ./cmd/server
```

Откройте [главную страницу](http://localhost:8080). Остановка — Ctrl+C.

Чтобы проверить реализованные рабочие разделы локально, запускайте сервер с тестовым входом:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true go run ./cmd/server
```

Откройте [вход](http://localhost:8080/auth/login) и используйте логин `dev_registry_staff` с паролем из закрытого `var/dev-users.txt`. После входа появится «Реестр фонда»: общежитие → корпус → этаж → комната → койко-место. Фотографии находятся в карточках общежития и комнаты, история статусов — в карточке места; статусы меняет `dev_commandant`. Список пользователей и смена ролей доступны `dev_system_admin` на `/admin/users`: в столбце «Роли» выберите новую роль и нажмите «Сохранить роль». Получатель увидит внутреннее уведомление в разделе «Уведомления»; новые права действуют без повторного входа. При обычном запуске вход выключен, поэтому рабочее меню не показывается. Если БД пуста, сначала создайте общежитие для назначенного `dev-dorm-1`; автоматическое создание пользователей не заполняет фонд. Комендант и администрация до создания записи переходят в реестр с пояснением.

Для запуска собранного приложения:

```sh
mkdir -p bin
go build -o bin/server ./cmd/server
./bin/server
```

HTML, CSS и миграции встроены в бинарник; при их изменении нужна пересборка. Бинарник может работать из другого каталога. Относительные пути данных вычисляются от рабочего каталога; для постоянного размещения задайте абсолютные пути.

## Демонстрация и проверка первого этапа

Демонстрационный фонд создаётся **только отдельной командой** в новую папку. Она отказывается работать вне development и не выполняется автоматически сервером:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true \
go run ./cmd/demo-data -out var/demo

APP_ENV=development DEV_LOGIN_ENABLED=true HTTP_ADDR=127.0.0.1:8090 \
DATABASE_PATH="$PWD/var/demo/dormitory.db" \
FILES_DIR="$PWD/var/demo/files" \
DEV_USERS_FILE="$PWD/var/demo/dev-users.txt" \
go run ./cmd/server
```

Демо открывается по [localhost:8090](http://localhost:8090). В `demo.json` — ID и ожидаемые количества, в закрытом `dev-users.txt` — индивидуальные пароли пяти ролей. Набор содержит полную иерархию, активную и архивную ветки, разрешённые статусы и три явно демонстрационных изображения. Активно: одно общежитие, две комнаты и пять мест — три свободных, одно на ремонте, одно временно недоступно. Комната 102 без фотографий даёт замечание статистики. Повтор в существующую папку запрещён; рабочий DATABASE_PATH команды не наполняется.

Результаты проверки чистого запуска, повторного запуска, ID/связей/вместимости, прав пяти ролей, CSRF/XSS, статусов, аудита, обновления каталога, RU/KK, мобильной вёрстки и восстановления — в [docs/mvp-verification.md](docs/mvp-verification.md). Составные пункты не объявлены завершёнными; оставшиеся ограничения перечислены там и в таблице требований.

## Реестр фонда

Откройте [реестр общежитий](http://localhost:8080/staff/dormitories) под сотрудником реестра. Новая запись общежития создаётся только для заранее назначенного ID. На карточке каждого родителя доступны список детей, добавление, редактирование и архивирование. Архивные записи и ссылки сохраняются; родителя с активными детьми архивировать нельзя. Есть восстановление. Все изменения требуют разрешения и назначения общежития, защищены CSRF и записываются с аудитом в одной транзакции.

Стоимость комнаты вводится целым числом минимальных денежных единиц с явными валютой и периодом. Форматы, маршрутная структура, ограничения и проверки описаны в [docs/inventory.md](docs/inventory.md). На карточке комнаты можно добавить койко-место с постоянным ID и уникальным обозначением. Места создаются свободными; вручную доступны только переходы свободно ↔ на ремонте и свободно ↔ временно недоступно. Для изменений обязательны основание, автор и время; история и аудит сохраняются атомарно. Устаревшая версия отклоняется с 409. Все неархивные места учитываются во вместимости; превышение и уменьшение вместимости ниже их числа запрещены. Забронировано и занято предусмотрены в модели для будущих процессов, ручного назначения нет. В текущей тестовой матрице структуру ведёт сотрудник реестра, статусы меняет комендант (`places.status.write`).

## Заявления студента

При development-входе войдите как `dev_student` (пароль в закрытом `var/dev-users.txt`). Из кабинета откройте [профиль](http://localhost:8080/student/profile) и [мои заявления](http://localhost:8080/applications). Заполните ФИО, email и учебную группу, создайте черновик, добавьте текст обращения, сохраните и отправьте с явным принятием тестового согласия. Карточка показывает номер, дату, источники полей и историю; повтор отправки не создаёт дубль. Отзыв разрешён только из «подано», до проверки, и сохраняет историю. Правило отзыва и шесть локальных статусов — проектное предложение. Текст согласия требует согласования, сведения введены студентом и не подтверждены. Добавлены закрытые документы PDF/JPEG/PNG до 10 МиБ с версиями и ручная проверка: `dev_administration` назначает `dev_registry_staff`, проверяющий запрашивает дополнение или завершает проверку с комментарием. Исправления требуют повторной отправки и проверки; номер регистрации сохраняется. Уведомления регистрации, дополнения и результата доступны в кабинете с признаком прочтения. «Проверено» не означает одобрение размещения и не даёт права бронирования. Очередь и комиссия не реализованы. Подробности и проверки — в [docs/applications.md](docs/applications.md). Новых настроек нет; миграции 000008/000009 применяются автоматически. Документы хранятся в закрытом `FILES_DIR/documents` отдельно от фотографий, выдаются только владельцу и назначенному проверяющему и включены в резервное копирование. Полный сценарий — [docs/application-review.md](docs/application-review.md).

## Фотографии

В карточках общежития и комнаты доступен раздел фотографий: добавление JPEG, PNG или WebP, описание, порядок, выбор основной и удаление. Лимиты: 5 МиБ, до 4096 пикселей по стороне и 12 миллионов пикселей. Изображения декодируются и записываются заново без EXIF и прочих метаданных; WebP сохраняется в PNG. Изменения требуют `registry.read`, `registry.write` и назначения общежития, проходят CSRF и транзакционный аудит.

Файлы находятся в закрытом `FILES_DIR/photos`, метаданные и связи — в SQLite. Хранилище подключено через небольшой интерфейс. Публичный `GET/HEAD /photos/{photoID}` доступен только у опубликованного общежития с активной цепочкой родителей; комнаты наследуют публикацию общежития. Закрытый просмотр — `/staff/photos/{photoID}` с правами на фактическое общежитие. При запуске и после загрузки/удаления очищаются файлы без метаданных; недостающий файл с записью в БД блокирует запуск. Хранилище должно соответствовать одной БД. Контракт, поведение при сбоях и перенос/резервирование пары БД и файлов — в [docs/photos.md](docs/photos.md).

## Публичный каталог

Откройте [каталог](http://localhost:8080/catalog) без входа. В нём видны только опубликованные неархивные общежития, фотографии и характеристики активных комнат, стоимость с валютой и периодом, свободные и все действующие места, время среза UTC. Количества рассчитываются по реальным неархивным местам с проверкой всей цепочки родителей. Пустой реестр даёт пустой каталог; демонстрационный фонд автоматически не создаётся. Бронирование пока недоступно.

Поиск по названию и адресу, фильтры по точной стоимости, валюте/периоду, свободным местам и доступности сохраняются в URL. Страница содержит до 12 общежитий. Суммы показываются в минимальных денежных единицах; для диапазона обязательны валюта и период. Каталог не передаёт в HTML сведения о пользователях, основаниях статусов, служебные записи или закрытые реквизиты оператора. Контракт и проверки — в [docs/catalog.md](docs/catalog.md).

Переключатель «Русский / Қазақша» доступен на всех HTML-страницах. Язык сохраняется в ссылках, формах, перенаправлениях и cookie; можно открыть `/catalog?lang=kk`. Переведены общие компоненты, каталог и существующие административные страницы, включая ошибки. Содержимое записей остаётся в исходном языке.

## Статистика, CSV и история

Войдите как `dev_administration`, чтобы открыть [статистику](http://localhost:8080/staff/statistics) и [историю изменений](http://localhost:8080/staff/history). Панель показывает действующие общежития, комнаты и реальные места, пять текущих статусов, распределение по назначенным общежитиям, неполные карточки и отсутствие фотографий. События и показатели чужого фонда не показываются; системный администратор не имеет обхода.

[Предпросмотр и фильтры экспорта](http://localhost:8080/staff/registry-export) и скачивание `/staff/registry.csv` доступны сотруднику реестра и администрации с отдельным `registry.export` и `registry.read`. CSV включает всю отфильтрованную выборку, поддерживает русский/казахский текст (UTF-8 с BOM) и защищает ячейки от выполнения формул. По умолчанию экспортируется активная цепочка; архив включается явным фильтром. История доступна только для чтения, с фильтрами и пагинацией; UPDATE/DELETE аудита дополнительно запрещены триггерами.

Миграция `000007_registry_export.sql` добавляет разрешение экспорта, индекс и защиту аудита. Она применяется автоматически, не перезаписывая пользователей и данные входа. Матрица, состав выборок, фильтры, CSV-контракт и доказательства проверок — в [docs/reports.md](docs/reports.md). Прогнозы и показатели несуществующих процессов не добавлены.

## Навигация и формы

На всех HTML-страницах есть общее меню, переход на главную, текущий раздел и понятные действия на страницах ошибок. После входа доступны кабинет, назначенные общежития и список пользователей — согласно текущим разрешениям. Выход доступен из шапки любой страницы и защищён CSRF. В кабинете отображаются роли и срок сеанса.

В списке пользователей работает GET-поиск по имени или ID с очисткой запроса и пустым состоянием. После ошибки входа форма сохраняет логин, очищает пароль и позволяет повторить попытку. Интерфейс адаптирован для узких экранов, поддерживает видимый фокус клавиатуры, подписи полей и хлебные крошки. Действия ещё не реализованных функций не выдаются за работающие кнопки.

HTML и CSS встроены в бинарник: уже запущенный сервер нужно перезапустить после сборки, чтобы увидеть изменения.

Проверка прежних 42 зарегистрированных маршрутов и навигации пяти ролей описана в [docs/routes-check.md](docs/routes-check.md); два публичных маршрута каталога и локализация — в [docs/catalog.md](docs/catalog.md), четыре закрытых маршрута отчётов — в [docs/reports.md](docs/reports.md).

## Тестовый вход

При включённом development-входе сервер после применения миграций автоматически создаёт по одному пользователю для каждой из пяти ролей:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true go run ./cmd/server
```

Данные входа сохраняются в отдельный текстовый файл `var/dev-users.txt` (по умолчанию рядом с БД; путь можно изменить через `DEV_USERS_FILE`). Откройте [форму входа](http://localhost:8080/auth/login). Логины: `dev_student`, `dev_registry_staff`, `dev_commandant`, `dev_administration`, `dev_system_admin`; у каждого свой случайный пароль из файла. Сотрудникам назначается область `dev-dorm-1`; само общежитие создаётся через реестр.

Файл создаётся с правами `0600`, новый каталог — `0700`; `dev-users*.txt` явно исключены в `.gitignore`. Пароли не выводятся в логи. Повторный запуск не меняет файл, локальные ID, пароли, роли и назначения, не восстанавливает отозванный доступ. Если полный набор уже создан прежней командой, используются прежние данные из её JSON-файла; новый TXT не создаётся, поскольку пароли в БД хранятся только как хеши. Частичный набор или существующий файл при отсутствии пользователей прерывают заполнение без перезаписи; для нового независимого набора нужны новая development-БД и новый файл.

Отдельная команда остаётся доступна для первоначального заполнения с другими назначениями, **до первого запуска сервера с включённым входом**:

```sh
APP_ENV=development DEV_LOGIN_ENABLED=true go run ./cmd/dev-users -out var/dev-users.json -dormitories dev-dorm-1,dev-dorm-2
```

По умолчанию тестовый вход и автозаполнение выключены. В production тестовый вход и создание тестовых пользователей запрещены, SSO остаётся отложенным. Production использует Secure cookie и требует HTTPS через доверенный обратный прокси. Матрица ролей и контракт идентификации описаны в [docs/auth.md](docs/auth.md).

## Вход с ЭЦП

Для всех ролей добавлен «Войти с ЭЦП»: NCALayer выбирает хранилище и запрашивает пароль ключа, собственный NCANode на сервере проверяет CMS, доверие, сроки и OCSP. Неизвестный проверенный ИИН создаёт аккаунт студента; у существующего аккаунта сохраняются ID, роли и назначения. ФИО/ИИН/email при наличии заполняются из сертификата, группа остаётся ручной. На `/student/profile` ИИН показан отдельным полем только для чтения; у уже вошедших пользователей он подхватывается из сохранённого проверенного сертификата без повторного входа. Пароль ключа и сам ключ сайту не передаются.

В проект добавлен [compose.ncanode.yaml](compose.ncanode.yaml) с NCANode 3.5.1, закреплённым digest, отдельным кешем и портом только на `127.0.0.1:14579`. Запустите Docker Desktop и сервис:

```sh
docker compose -f compose.ncanode.yaml up -d --wait
```

В закрытом `.env` задайте `NCANODE_URL=http://127.0.0.1:14579` и `EDS_ORIGIN=http://localhost:8080`. Для запуска сайта с этим файлом:

```sh
./scripts/run-local.sh
```

Скрипт загружает `.env`, собирает актуальный бинарник и запускает его. Текущие локальные БД/файлы сохраняются. Остановка NCANode — `docker compose -f compose.ncanode.yaml stop`, повторный запуск — `up -d --wait`; том кеша сохраняется. Сервер по-прежнему не загружает `.env` самостоятельно при прямом `go run`.

Альтернатива с явным окружением:

```sh
DEV_LOGIN_ENABLED=false \
NCANODE_URL=http://127.0.0.1:14579 \
EDS_ORIGIN=http://localhost:8080 \
go run ./cmd/server
```

Откройте [вход](http://localhost:8080/auth/login). Для production нужны HTTPS и соответствующий `EDS_ORIGIN`. Для первого администратора и привязки существующих сотрудников предусмотрена офлайн-команда `cmd/eds-account` без паролей, с закрытым файлом ИИН. Подробные команды, ограничения и проверка реальным ключом — в [docs/eds-login.md](docs/eds-login.md). Локальный NCANode настроен и проверен на настоящем API; вход действительным пользовательским ключом и его OCSP-проверка ещё требуют сквозного прогона. Подробности фактической настройки — в конце инструкции. Вузовский SSO остаётся отложенным.

| --- | --- | --- |
| `HTTP_ADDR` | `localhost:8080` | TCP-адрес host:port. Внешний адрес задаётся явно. |
| `DATABASE_PATH` | `var/dormitory.db` | Путь к постоянному файлу SQLite; URI и `:memory:` не принимаются. |
| `FILES_DIR` | `var/files` | Закрытый каталог рабочих файлов; фотографии в подкаталоге `photos`. Не публиковать статическим маршрутом, не разделять между разными БД. |
| `APP_ENV` | `development` | `development` или `production`; неизвестные значения запрещены. |
| `DEV_LOGIN_ENABLED` | `false` | Включить тестовый вход и заполнение пяти ролей после миграций; в production значение true запрещает запуск. |
| `DEV_USERS_FILE` | `dev-users.txt` рядом с `DATABASE_PATH` | Закрытый текстовый файл данных входа при первоначальном заполнении. Используйте исключённые из Git пути. |
| `NCANODE_URL` | пусто | Собственный NCANode API v3: HTTPS либо loopback HTTP. Пусто выключает вход с ЭЦП и NCA-сессии. |
| `EDS_ORIGIN` | `http://localhost:8080` | Публичный origin сайта в одноразовом запросе подписи, без пути/query; в production только HTTPS. |
| `SESSION_TTL` | `8h` | Абсолютный срок сессии, от 1s до 24h. |
| `SHUTDOWN_TIMEOUT` | `10s` | Положительная длительность ожидания активных запросов при завершении. |

Переменные читаются из окружения; `.env` автоматически не загружается. Пример без секретов можно явно загрузить в POSIX shell или zsh:

```sh
cp .env.example .env
set -a
. ./.env
set +a
go run ./cmd/server
```

Пустое или некорректное значение приводит к ошибке запуска. Каталоги данных создаются с правами `0700`, новый файл БД — `0600`; существующие права не меняются. Ошибки конфигурации, БД, миграций и занятого порта завершают процесс с ненулевым кодом. Журнал JSON выводится в stdout; внутренние ошибки не раскрываются в HTML. Рабочие БД, WAL/SHM/journal-файлы, `.env`, локальные файлы окружения и каталог `secrets` исключены из Git; `.env.example` остаётся доступным для коммита.

Каждый HTTP-запрос получает новый серверный `request_id`: он возвращается в `X-Request-ID`, передаётся через `context.Context` и записывается в технический журнал. Входящий `X-Request-ID` не используется. В журнал не попадают тела, заголовки, query string, сырой URL или значение паники. Вместо пути записывается шаблон маршрута либо `unmatched`. Пароли, токены, содержимое документов и полные анкеты не должны передаваться в технические логи и сообщения ошибок.

## Маршруты

| Адрес | Ответ |
| --- | --- |
| `GET /` | Главная в общем HTML-шаблоне. |
| `GET /catalog` | Публичный список, поиск, фильтры и пагинация. |
| `GET /catalog/{dormitoryID}` | Публичная карточка с активными комнатами, фото, стоимостью и доступностью. |
| `GET /healthz` | `200` и `{"status":"ok"}`, если SQLite отвечает; иначе `503` и `{"status":"unavailable"}`. Таймаут проверки — 1 секунда. Это проверка БД, не готовности бизнес-функций. |
| `GET /static/app.css`, `GET /static/ncalayer-login.js` | Встроенные публичные CSS и клиент NCALayer; другие пути не публикуются. |
| Неизвестный путь | Общая HTML-страница `404`. |
| Неподдерживаемый метод известного пути | Общая HTML-страница `405`, `Allow: GET, HEAD`. |

Маршруты auth: `GET /auth/login` (при настроенном NCANode или включённом development-входе), `POST /auth/login` (только development), `POST /auth/eds/challenge`, `POST /auth/eds/login` (при настроенном NCANode), `GET /account`, `POST /auth/logout`, `GET /admin/users`, `POST /admin/users/{userID}/role`, `GET /account/notifications`, `POST /account/role-notifications/{notificationID}/read` и `GET /staff/dormitories/{dormitoryID}`. Защищённые адреса проверяют права на сервере, включая прямые запросы.

Для маршрутов чтения поддерживается HEAD; выход разрешён только через POST. Паника до отправки ответа журналируется и возвращает общую страницу `500`; после начала ответа соединение прерывается. Шаблоны проверяются при запуске. Общие, публичные и существующие административные страницы поддерживают `ru` и `kk`; редакционное утверждение перевода и расширенная матрица устройств остаются по Q-10.

## Миграции и данные

SQL-файлы `migrations` имеют непрерывную нумерацию с шести цифр. Первая миграция создаёт `schema_migrations` с именем, SHA-256 и временем применения. Перед запуском HTTP новые миграции выполняются по порядку в одной транзакции. Повторный запуск не применяет их заново. Изменённый применённый файл, несовместимая история или ошибка SQL прерывают запуск и откатывают транзакцию.

Изменения схемы добавляются новым SQL-файлом. Автоматического отката схемы и отдельной команды миграций нет. Драйвер включает `foreign_keys=ON`, WAL, `synchronous=FULL` и `busy_timeout=5000` при открытии каждого физического соединения, включая замену соединений в пуле. Пул настроен явно: максимум одно открытое и одно простаивающее соединение, без ограничения времени жизни и простоя. Ожидание места в пуле и запросы получают контекст вызывающей операции. Вызов SQLite, ожидающий блокировку, может завершиться по `busy_timeout` позже срока контекста; короткий контекст не заменяет ограничение занятости.

Все связанные изменения выполняются через `database.WithinTx`. Для обязательного аудита используется `audit.NewRecorder(db).RecordChange`: callback выполняет деловое изменение через переданный `*sql.Tx`, возвращает событие, и вставка в `audit_events` происходит до общего `COMMIT`. Ошибка изменения, записи аудита или фиксации, отмена контекста и паника откатывают транзакцию. Значения передаются в SQL параметрами. Контракт и ограничения — в [docs/sqlite.md](docs/sqlite.md).

Событие содержит автора, время UTC, действие, тип и ID объекта, результат и `request_id`. Документы, профили и секреты в событии не хранятся. История мест с основаниями, автором, временем и старым/новым статусами доступна на закрытой карточке по правам фонда. Чтение аудита реестра по назначенным общежитиям и запрет изменения/удаления через приложение реализованы. Общий журнал событий без общежития, политика хранения и эксплуатационная защита остаются отдельной работой.

Основа рассчитана на один экземпляр с постоянным локальным диском. Добавлены ручные согласованные копии SQLite и фотографий с проверкой WAL, SHA-256, целостности и FK; восстановление проверено в отдельную папку. Сервер и изменяющие CLI-команды удерживают межпроцессные блокировки БД и хранилища, не допускают второй процесс и незавершённые maintenance-папки. Копирование одного основного файла активной WAL-БД не поддерживается; контракт — [docs/backup.md](docs/backup.md).

## Резервная копия и восстановление

Сначала остановите сервер Ctrl+C/SIGTERM и дождитесь корректного завершения. Затем, из корня проекта, с новыми выходными папками:

```sh
DATABASE_PATH="$PWD/var/demo/dormitory.db" \
FILES_DIR="$PWD/var/demo/files" \
go run ./cmd/backup create -out var/backups/mvp-001

go run ./cmd/backup verify -from var/backups/mvp-001

go run ./cmd/backup restore \
  -from var/backups/mvp-001 -out var/restored-mvp-001

APP_ENV=development DEV_LOGIN_ENABLED=true HTTP_ADDR=127.0.0.1:8090 \
DATABASE_PATH="$PWD/var/restored-mvp-001/dormitory.db" \
FILES_DIR="$PWD/var/restored-mvp-001/files" \
DEV_USERS_FILE="$PWD/var/demo/dev-users.txt" \
go run ./cmd/server
```

Команда создаёт самостоятельную SQLite через `VACUUM INTO`, читая подтверждённый WAL, и копирует **все связанные** фотографии, включая архив. Верификация проверяет журнал миграций, integrity/FK, manifest, размеры и SHA-256. `restore` не перезаписывает существующую папку. `.env`, plaintext-файл паролей и посторонние рабочие файлы в комплект не входят; для development-входа сохраняйте исходный `dev-users.txt`. Сессии и хеши в SQLite сохраняются.

Неполный набор имеет `.maintenance-incomplete`, и приложение отказывается его открывать. Не удаляйте маркер/lock-файлы для обхода отказа. При ошибке используйте новую папку. Подробности, ограничения офлайн-режима и команды — в [docs/backup.md](docs/backup.md).

## Структура

```text
cmd/server/                   запуск, сигналы, завершение
cmd/demo-data/                явный изолированный development-набор
cmd/backup/                   create/verify/restore согласованной пары
internal/app/                 сборка зависимостей и маршруты
internal/platform/config/     окружение и проверка настроек
internal/platform/database/   SQLite и миграции
internal/platform/httpserver/ middleware, HTML, healthz
internal/platform/files/      закрытое файловое хранилище
internal/platform/maintenance/ блокировки процессов и неполных наборов
internal/platform/backup/     SQLite-снимок, manifest, файлы и восстановление
internal/platform/requestid/  ID операции в контексте без зависимости от HTTP
internal/modules/inventory/   реестр общежитий, корпусов, этажей, комнат и мест
internal/modules/auth/        пользователи, идентичности, права, сессии, CSRF
internal/modules/audit/       запись событий, неизменяемый аудит и чтение истории
internal/modules/reports/     закрытая статистика, CSV и история по правам
web/templates/                общий шаблон, главная, ошибки

migrations/                   последовательные SQL-миграции
docs/                         требования и открытые вопросы
```

В бизнес-модулях разделяются обработчики, сервисы и репозитории. SQL не находится в HTTP-слое, сервисы не зависят от HTTP, зависимости передаются конструкторами. Отложенные интеграции и правила полного цикла размещения не добавлены.

## Проверки

```sh
gofmt -w cmd internal migrations web
go test ./...
go vet ./...
mkdir -p bin
go build -o bin/server ./cmd/server
```

Тесты используют временные БД: создание и обновление прежней БД, повтор миграций, откат SQL и проверка истории, реальные нарушения внешних ключей на нескольких соединениях и после их замены, WAL и ожидание блокировки. Проверяются совместные фиксация и откат изменения с аудитом, ошибка `COMMIT`, отмена контекста, паника, `request_id` и отсутствие чувствительных данных в техническом журнале. Проверки auth включают пять ролей, прямые URL, CSRF, отзыв и срок сессий, безопасные cookie, запрет development-входа в production и отдельную команду пользователей. Автозаполнение проверяется на первом и повторном запуске, при ошибках файла и аудита, частичном наборе и выключенном development-входе. Фиктивные предметные таблицы создаются только внутри тестов и не входят в миграции продукта.

При работающем сервере в другом терминале:

```sh
curl --fail-with-body http://localhost:8080/healthz
curl --fail-with-body http://localhost:8080/
curl --fail-with-body http://localhost:8080/static/app.css
curl -i http://localhost:8080/missing
curl -i -X POST http://localhost:8080/
```

Последние команды должны показать `404` и `405`. Остановите сервер и запустите с тем же `DATABASE_PATH`: первая миграция не должна записываться повторно. SIGTERM проверяется на собранном бинарнике командой `kill -TERM <PID>` из другого терминала; нормальное завершение оставляет сообщение `server stopped gracefully` и код выхода 0.

Проверки койко-мест включают запрещённые переходы, откат статуса/истории при ошибке аудита, конфликт двух одновременных изменений и гонки вместимости. Схема расширена миграцией `000005_inventory_beds.sql`; прежние миграции сохранены.

Проверки фотографий, сбоев хранилища и прав описаны в [docs/photos.md](docs/photos.md). Схема расширена миграцией `000006_inventory_photos.sql`; прежние миграции не изменены.

Проверки каталога, публичной модели, согласованности с реестром и русского/казахского интерфейсов описаны в [docs/catalog.md](docs/catalog.md). Новых настроек и миграций для каталога нет.

Проверки статистики, CSV, истории, пяти ролей, отзыва назначений и защиты выгрузки от формул — в [docs/reports.md](docs/reports.md). Настроек окружения для отчётов не добавлено.

Сквозная проверка первого этапа и точные команды — [docs/mvp-verification.md](docs/mvp-verification.md). Новые тесты проверяют полное восстановление, данные из WAL, межпроцессные блокировки и реальный SIGTERM. Резервное копирование по расписанию, offsite/шифрование, ротация, RPO/RTO и производственная приёмка остаются отдельной работой.

Проверки и настройка ЭЦП — [docs/eds-login.md](docs/eds-login.md). Миграция `000011_eds_login.sql` сохраняет существующие ID/роли и добавляет сертификатный профиль, уникальную связь NCA и одноразовые запросы. Дополнительная клиентская проверка: `node --test web/tests/ncalayer-login.test.cjs`; сервер использует только Go и собственный NCANode.
